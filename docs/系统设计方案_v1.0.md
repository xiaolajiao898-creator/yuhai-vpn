## 0. 编码前需要确认的关键结论

以下几点会直接影响技术路线或上线可行性，建议开工前先确认。

| # | 事项 | 结论与建议 |
|---|---|---|
| 1 | iOS 分发 | 企业签名面向公众分发违反 Apple 企业开发者计划协议，证书被吊销后所有用户的 App 会立即无法打开；市面上的"企业签"多为租用他人证书，还存在安装包被植入代码的风险。免费 Apple ID 自签不支持 Network Extension 能力，VPN 功能无法工作。描述文件（.mobileconfig）不能安装 App，只能下发系统原生的 IKEv2/IPSec 配置。**建议：TestFlight 作为主渠道，Ad Hoc 用于内测，IKEv2 描述文件作为兜底。** 详见第 13 章。 |
| 2 | Android 开发者验证 | Google 自 2026-09-30 起在巴西、印尼、新加坡、泰国，对从参与计划的应用商店（Google Play、Galaxy Store 等）安装的应用执行开发者验证；2027 年扩展到全球认证设备上的所有应用，届时官网直装的 APK 也会受影响。未注册开发者的应用需要用户走"高级安装流程"（一次性设置，含 24 小时等待）或使用 ADB。**建议：以公司主体完成 Android 开发者验证并登记包名与签名证书。** 这意味着运营方需要对 Google 实名，但不影响终端用户匿名。 |
| 3 | 开源内核许可证 | sing-box 为 GPL-3.0（另附名称使用限制），闭源 App 直接链接可能触发开源义务；Xray-core 为 MPL-2.0，相对宽松；WireGuard 官方实现为 MIT/Apache-2.0。**阶段二接入前必须完成许可证评审**，阶段一使用模拟引擎不受影响。 |
| 4 | 无手机号/邮箱的找回 | 账户密钥是唯一找回凭证，丢失即无法找回，必须在 UI 中强引导备份。账户密钥是登录凭证，不是钱包私钥或助记词，与"App 不保存私钥、助记词"不冲突。 |
| 5 | 唯一金额的局限 | 部分交易所提币会从到账数量中扣手续费或不支持 4 位小数，会导致金额不符。必须有"异常到账"人工处理流程，支付页要明确提示"到账数量需等于订单金额"。 |
| 6 | 宣传用语 | 避免"绝对匿名""100% 安全""无法追踪"等无法证明的说法，这类表述有虚假宣传风险，也会损害信任。建议使用"加密传输""不记录浏览内容"等可验证的表述，并确保隐私政策与实际实现一致。 |
| 7 | 合规 | VPN 服务与加密货币收款在不同国家和地区有不同的许可、反洗钱与税务要求，部分地区限制未经许可的 VPN 服务；节点所在机房也有滥用处理条款。上线前请按目标市场咨询当地律师（本文不构成法律意见）。邀请奖励建议只做一级，多级返利在部分地区可能被认定为传销。 |

## 1. 产品定位与阶段范围

### 1.1 定位

宇海加密VPN 是一款面向注重隐私用户的跨平台加密网络工具。用户不需要提供手机号、邮箱或任何身份信息，安装后即可进入，通过 USDT-TRC20 自助开通套餐。体验上追求两件事：稳，连接一次成功、断线自动恢复；简，首页一眼看懂自己是否受保护、还剩多少时间和流量。

### 1.2 设计原则

| 原则 | 含义 |
|---|---|
| 模拟的是数据源，不是业务逻辑 | 模拟 VPN 引擎、模拟链上数据源与真实实现共用同一接口。阶段一的入账、开通、奖励、流水代码就是生产代码，阶段二只替换适配器。 |
| 资金一律用整数 | 金额统一以 micro-USDT（1 USDT = 1,000,000）存储和计算，禁止浮点数。接口中金额以字符串传输。 |
| 先有流水，才有余额 | 余额、时长、流量、设备数的任何变化都必须写流水；快照可以由流水完整重算。 |
| 数据最小化 | 不收集业务不需要的数据；能存哈希就不存明文；能聚合就不存明细。 |
| 客户端不可信 | 价格、应付金额、折算、权益、设备上限全部由服务端计算，客户端只负责展示。 |
| 高风险操作可追溯、可复核 | 后台敏感操作需要二级验证，资金与权益调整需要第二人批准，所有操作写入防篡改审计日志。 |

### 1.3 阶段范围

| 模块 | 阶段一：可演示版 | 阶段二：真实服务 | 阶段三：增强 |
|---|---|---|---|
| App 界面 | 全部页面、深色主题、潮汐环连接动画 | 多语言、性能与省电优化 | 分应用代理（Android）、小组件 |
| 连接 | 模拟引擎：状态机、模拟速率与流量、模拟延迟 | 真实内核（VLESS-Reality / Trojan / SS-2022 / WireGuard）、自动选点、断线重连、防泄漏 | Hysteria2、IKEv2 描述文件兜底 |
| 账户 | 匿名注册、账户密钥备份与恢复、设备管理 | 设备密钥签名、App Attest / 设备完整性评估 | 迁移二维码加密 |
| 套餐 | 按天、按月、流量包、设备加购、升级折算 | 同左 | 促销与优惠码 |
| 充值 | 真实订单与唯一金额；后台"模拟到账"走真实到账事务 | TronGrid 只读扫描、自动到账 | 自建 TRON 节点双源校验 |
| 邀请 | 邀请码、链接、手动与剪贴板绑定、奖励规则、冻结期、防刷规则 | APK 渠道包写入邀请码 | 分享海报模板、渠道码统计 |
| 节点 | 节点与入站管理、模拟负载与心跳 | node-agent、Xray/WireGuard 用户同步、真实流量统计 | 多点健康探测、智能调度 |
| 后台 | 全部管理页面、TOTP、二级验证、双人复核、审计哈希链 | 告警、对账报表 | 细粒度数据权限 |
| 分发 | 演示 APK、Ad Hoc 包 | 官网下载页、应用内更新、TestFlight | 欧盟替代分发评估 |

## 2. 总体架构

### 2.1 架构总览

```
[用户设备] 宇海加密VPN App（Flutter UI + 原生 VPN 扩展）
    │
    ├── ① HTTPS API（TLS 1.3、证书固定、设备签名）
    │         │
    │         ▼
    │   [公网接入层] CDN / WAF → API 网关（限流、防重放）
    │         │
    │         ▼
    │   [业务区 · 私网]
    │     app-api ─────────── 节点控制面（mTLS）◄──────────┐
    │     worker（链上只读扫描 / 到账 / 到期 / 奖励 / outbox）│
    │         │                                          │
    │         ▼                                          │
    │   [数据区] PostgreSQL（主从 + 时间点恢复）   Redis     │
    │         ▲                                          │
    │         │ 受限数据库角色                              │
    │   [管理区 · 内网] admin-web → admin-api              │
    │     （零信任网关 + IP 白名单 + TOTP + 二级验证 + 审计链）│
    │                                                    │
    └── ② 加密隧道（VLESS-Reality / Trojan / SS-2022 / WireGuard）
              │                                          │
              ▼                                          │
        [节点集群] Xray-core + WireGuard + node-agent ─────┘

[TRON 链] ◄── 只读查询 ── worker
[TRON 链] ◄── 多签出款 ── [资金系统 · 独立网络 / 独立仓库 / 独立人员]
                              └── 只读拉取对账数据，业务系统无法调用其任何写操作
```

### 2.2 服务职责

| 服务 | 代码位置 | 职责 | 部署位置 |
|---|---|---|---|
| app-api | server/cmd/api | App 全部接口：匿名账户、设备、套餐、报价、订单、节点配置、邀请、版本检查 | 业务区，经 CDN/WAF 暴露 |
| 节点控制面 | 与 app-api 同进程，独立端口与路由组 | 节点注册、心跳、用户增量同步、流量上报 | 业务区，mTLS 暴露给节点 |
| admin-api | server/cmd/admin-api | 后台接口、RBAC、二级验证、审批、审计 | 管理区，不暴露公网 |
| worker | server/cmd/worker | 链上扫描、到账事务、订单过期、订阅到期、流量周期重置、奖励释放、outbox 投递、每日对账 | 业务区，无入站端口 |
| node-agent | server/cmd/node-agent | 部署在每台节点：同步用户到 Xray/WireGuard、采集流量、上报心跳 | 各节点 |
| admin-web | apps/admin-web | 后台前端静态资源 | 管理区 |
| website | apps/website | 官网、下载页、邀请落地页、帮助中心 | 公网 CDN |
| 资金系统 | 独立仓库 | 多签钱包、归集、出款、对账（本项目不实现） | 资金区 |

阶段一采用"模块化单体"：app-api、admin-api、worker 共用 `internal` 下的业务模块，编译为三个独立二进制，共享一个数据库。业务边界按包划分，模块之间只通过接口调用，将来需要时再拆成独立服务。

### 2.3 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 移动端 UI | Flutter（Dart），Riverpod，go_router，dio | 双端共用一套 UI；自绘渲染便于实现高质量动效，不受原生组件外观限制 |
| Android VPN | Kotlin，VpnService，前台服务 | 系统标准 VPN 接口 |
| iOS VPN | Swift，NetworkExtension（NEPacketTunnelProvider） | iOS 上第三方隧道的唯一正规方式 |
| 隧道内核 | 阶段一：模拟引擎；阶段二：sing-box 或 Xray-core（gomobile 编译）+ WireGuard 官方库 | 使用成熟开源实现，不自研加密协议；最终选择取决于许可证评审（见 3.5） |
| 后端 | Go（当前稳定版），Gin，sqlc + pgx，goose 迁移 | 强类型；并发模型适合链上轮询与节点通信；sqlc 让资金相关 SQL 显式、可审查 |
| 数据库 | PostgreSQL 17 及以上 | 事务、行锁、部分唯一索引、CHECK 约束、分区表，适合账务场景 |
| 缓存与任务 | Redis 7+，Asynq | 限流、nonce 防重放、在线状态、异步任务 |
| 管理后台 | React + TypeScript + Vite + Ant Design + TanStack Query | 表格与表单密集型后台开发效率高 |
| 官网 | Astro 静态生成 | 加载快，便于 CDN 分发下载页与邀请落地页 |
| 节点内核 | Xray-core（服务端）+ Linux 内核 WireGuard | Xray 提供 gRPC API，可在不重启的情况下增删用户并按用户统计流量 |
| 链上数据 | 阶段二 TronGrid API；阶段三增加自建 java-tron 节点 | 只读查询，业务系统中没有任何私钥 |
| 接口契约 | OpenAPI 3.1 | App 与后台的类型从同一份规范生成，减少联调错误 |
| 可观测性 | Prometheus + Grafana + Loki；可选自建 Sentry | 日志不含用户访问内容；不接入第三方统计 SDK |
| 密钥管理 | HashiCorp Vault 或云 KMS | 字段加密密钥、JWT 签名密钥、HMAC pepper 与代码、数据分离 |
| 部署 | 阶段一 Docker Compose；后续 Kubernetes 或 Nomad | 渐进演进 |

### 2.4 网络分区

| 区域 | 包含 | 允许入站 | 允许出站 |
|---|---|---|---|
| 公网接入区 | CDN/WAF、API 网关 | 443 | 仅业务区 app-api |
| 业务区 | app-api、节点控制面、worker | 仅来自网关；节点 mTLS | TronGrid、数据区 |
| 数据区 | PostgreSQL、Redis | 仅业务区、管理区 | 加密备份存储 |
| 管理区 | admin-web、admin-api | 仅运维 VPN / 零信任网关，叠加 IP 白名单 | 数据区（受限角色） |
| 节点区 | 各地 VPN 节点 | 用户隧道端口；SSH 仅来自堡垒机 | 节点控制面 mTLS |
| 资金区 | 资金系统 | 无公网入站 | TRON 网络；只读拉取业务区对账数据 |

### 3.2 VPN 引擎抽象

```dart
enum VpnStatus { disconnected, connecting, connected, reconnecting, disconnecting, error }

class VpnStats {
  const VpnStats({
    required this.upBytes,
    required this.downBytes,
    required this.upSpeed,
    required this.downSpeed,
    required this.since,
  });
  final int upBytes;    // 本次连接累计上行字节
  final int downBytes;  // 本次连接累计下行字节
  final int upSpeed;    // 字节/秒
  final int downSpeed;  // 字节/秒
  final DateTime since; // 连接建立时间
}

class VpnFailure {
  const VpnFailure(this.code, this.message);
  // HANDSHAKE_TIMEOUT / AUTH_REJECTED / PERMISSION_DENIED / NETWORK_UNAVAILABLE / PROFILE_EXPIRED
  final String code;
  final String message;
}

abstract interface class VpnEngine {
  Stream<VpnStatus> get status;
  Stream<VpnStats> get stats;
  Stream<VpnFailure> get failures;

  /// 申请系统 VPN 权限：Android 首次弹出系统授权；iOS 安装 VPN 配置
  Future<bool> prepare();

  Future<void> connect(ConnectProfile profile);
  Future<void> disconnect();

  /// 到节点探测端口的 TCP 连接耗时（毫秒），失败返回 null
  Future<int?> probe(String host, int port, {Duration timeout = const Duration(seconds: 2)});
}
```

阶段一的 `MockVpnEngine`：调用 `connect` 后随机等待 1.2 到 2.0 秒进入 `connected`，有 5% 概率返回 `HANDSHAKE_TIMEOUT` 用于演示失败态；连接期间每秒产生模拟速率与累计流量；`probe` 按节点地区返回稳定的伪随机延迟。阶段二替换为 `NativeVpnEngine` 后，UI 与状态机代码不需要改动。

### 3.3 连接状态机

```
                connect()                  握手成功
 disconnected ───────────► connecting ────────────► connected
      ▲                        │                        │
      │                        │ 握手失败                │ 隧道中断 / 探测失败 / 网络切换
      │ disconnect()           ▼                        ▼
      │                      error ◄── 超过 2 分钟 ── reconnecting ── 恢复 ──► connected
      │                        │
      └──── 用户关闭提示 ───────┘
```

| 事件 | 行为 |
|---|---|
| 用户点击连接，未开通套餐 | 不进入状态机，直接跳转套餐页 |
| 用户点击连接，已开通 | 获取或复用连接配置 → `prepare` → `connect` |
| 连接配置过期或被拒绝（AUTH_REJECTED） | 重新拉取配置后重试一次；仍失败则刷新账户状态（可能已到期或设备被移除） |
| 握手超时 | 按 3.5 的协议顺序尝试下一个协议；全部失败切换备选节点 |
| 已连接时网络中断 | 进入 `reconnecting`，按 3.7 的策略重试 |
| 服务端推送不可连接（到期、流量用尽、设备移除） | 断开并在首页展示对应状态 |

### 3.4 原生实现要点

**Android**

- `YuhaiVpnService : VpnService`，以前台服务运行，通知栏常驻连接状态与"断开"操作。Android 14 及以上需要在清单中声明前台服务类型，VPN 场景的类型选择以官方文档为准。
- 隧道内核以 AAR 形式集成（gomobile 编译），在服务进程中运行。
- 通过 `EventChannel` 向 Flutter 推送状态与统计；应用被系统回收后，服务独立存活，重新打开 App 时读取服务当前状态。
- 引导用户在系统设置中开启"始终开启的 VPN"与"屏蔽未使用 VPN 的连接"，App 内提供跳转入口（`Settings.ACTION_VPN_SETTINGS`），App 本身无法代替用户开启。
- 阶段三：分应用代理（`addAllowedApplication` / `addDisallowedApplication`）。

**iOS**

- 主 App 与 Packet Tunnel 扩展两个 target，通过 App Group 共享配置与状态，通过共享 Keychain 访问组共享凭证。
- 主 App 使用 `NETunnelProviderManager` 安装和启动配置，通过 `sendProviderMessage` 获取实时统计。
- 自动重连使用 `NEOnDemandRuleConnect`，由系统在网络可用时拉起隧道。
- "断网保护"开关对应 `includeAllNetworks`，开启后隧道断开时流量被阻断；它会影响部分本地网络功能，开关旁需要说明。
- Packet Tunnel 扩展有严格的内存上限（约 50 MB），Go 内核需要设置内存上限（`debug.SetMemoryLimit`）并精简路由规则集，阶段二必须在低端机型上做压力测试。

### 3.5 协议策略与内核选择

| 协议 | 定位 | 说明 |
|---|---|---|
| VLESS + Reality + Vision | 默认首选 | TCP 443，基于 TLS 1.3，无需为节点购买域名证书，兼容性和稳定性好 |
| Trojan（TLS） | 第一备选 | 需要域名与证书，实现成熟 |
| Shadowsocks 2022 | 第二备选 | AEAD-2022 加密，配置简单，资源占用低 |
| WireGuard | 高速模式 | UDP，速度快、省电；UDP 受限的网络下不可用，因此不作为默认 |
| Hysteria2 | 阶段三可选 | 基于 QUIC，适合高丢包网络 |

自动选择协议：按"用户偏好 → 服务端下发的推荐顺序"依次尝试，单次握手 8 秒超时即切换下一个；成功的协议在该节点上缓存 24 小时。

| 内核方案 | 组成 | 许可证 | 优点 | 代价 |
|---|---|---|---|---|
| A | sing-box（libbox） | GPL-3.0，附名称使用限制 | 协议最全，移动端集成成熟，自带 URL 测速与路由 | 闭源分发存在许可证风险，需法务评估或开放客户端源码 |
| B | Xray-core + TUN 转发库 | Xray 为 MPL-2.0；TUN 库需逐一核对 | 许可证相对宽松；与服务端内核一致 | 移动端集成工作量更大 |
| C | WireGuard 官方库（wireguard-go / wireguard-apple / wireguard-android） | MIT / Apache-2.0 | 许可证宽松，实现可靠 | 仅支持 WireGuard |

建议：阶段二开始前完成许可证评审。若能接受开放客户端源码或取得授权，采用 A；否则采用 B + C。无论选哪种，都通过 `VpnEngine` 接口隔离，上层代码不受影响。

### 3.6 自动选点与测速

```
输入：可用节点列表（服务端已按套餐等级过滤，附带负载 load 0–100 与推荐标记）

1. 并发探测，并发上限 8：对每个节点的探测端点做 3 次 TCP 连接计时，单次超时 2 秒
2. rtt  = 成功结果的中位数
   loss = 失败次数 / 3；loss = 1 的节点直接排除
3. score = rtt × (1 + 2 × loss) × (1 + 0.5 × load / 100)
   用户收藏地区内的节点 score × 0.85
4. 取 score 最小的节点；前 3 名作为重连时的备选
5. 结果缓存 10 分钟；网络类型变化（Wi-Fi 与蜂窝切换）或用户下拉刷新时立即失效
```

已连接状态下，直接探测会被路由进隧道导致结果失真。处理方式：由隧道内核在隧道内做 URL 测速，或把各节点地址排除出隧道路由后直连测量。iOS 主 App 中不能使用 ICMP，统一使用 TCP 连接计时。

延迟显示规则：100 ms 以下为月白色，100 到 250 ms 为雾色，250 ms 以上为星辉色，超时显示"超时"。

### 3.7 断线重连

- 触发条件：隧道内核报告连接中断；每 15 秒一次的隧道内探测连续失败 3 次；系统网络切换。
- 退避间隔：1、2、4、8、16、30 秒，上限 30 秒，每次叠加正负 20% 随机抖动。
- 同一节点连续失败 3 次后切换到备选节点。
- 累计 2 分钟仍未恢复则进入 `error`，通过通知告知用户。
- 收到"网络已恢复"事件时立即重试一次，不等待退避。

### 3.8 防泄漏

| 风险 | 措施 |
|---|---|
| DNS 泄漏 | 所有 DNS 查询经隧道发往节点侧解析或加密 DNS，阻止系统 DNS 旁路 |
| IPv6 泄漏 | 节点支持 IPv6 时经隧道路由；不支持时 TUN 接管 `::/0` 并丢弃 |
| 隧道断开时明文外泄 | Android 引导开启系统"屏蔽未使用 VPN 的连接"；iOS 提供 `includeAllNetworks` 断网保护开关 |
| 重连窗口期 | 重连期间保持 TUN 接口不释放，流量排队或丢弃，不回落到直连 |

### 3.9 客户端本地数据

| 数据 | 存储位置 | 说明 |
|---|---|---|
| 设备签名私钥 | iOS Secure Enclave；Android Keystore（优先 StrongBox） | 不可导出 |
| 账户密钥 | Keychain / Keystore 保护的安全存储 | 查看需生物认证或设备密码 |
| 访问令牌、刷新令牌 | 安全存储 | 退出登录时清除 |
| WireGuard 私钥 | 安全存储；iOS 放在共享 Keychain 供扩展读取 | 从不上传 |
| 连接配置（含设备凭证） | 安全存储；iOS 通过 App Group 传给扩展 | 24 小时过期后重新获取 |
| 节点列表、测速缓存 | 普通缓存文件 | 不含凭证，可随时清除 |
| 运行日志 | 仅内存环形缓冲区；用户主动"导出诊断信息"时才写入文件 | 不含访问目标地址 |

App 不集成任何第三方统计或广告 SDK。崩溃上报默认关闭，用户在设置中主动开启后才上传到自建服务。

### 3.10 应用更新

## 4. 匿名账户体系

### 4.1 标识与凭证

| 名称 | 格式 | 用途 | 服务端存储 |
|---|---|---|---|
| 账户号 | 10 位数字，显示为 `8302 5716 44` | 展示、客服查询；本身不能用于登录 | 明文 |
| 账户密钥 | `YH-` 前缀加 20 位 Crockford Base32（不含 I、L、O、U），分组显示为 `YH-7KQ2-MX9R-TAHD-4PWN-3E8C`，约 100 bit 熵 | 恢复账户、新设备登录 | `HMAC-SHA256(pepper, 密钥)`，pepper 存于 KMS |
| 设备密钥 | P-256 密钥对，私钥在安全硬件中且不可导出 | 请求签名、刷新令牌绑定设备 | 仅公钥 |
| 访问令牌 | JWT（EdDSA 签名），有效期 15 分钟 | 普通接口鉴权 | 不存储 |
| 刷新令牌 | 256 bit 随机值，有效期 30 天，每次使用后轮换 | 换取新的访问令牌 | SHA-256 哈希 |

账户密钥熵足够高，用带 pepper 的 HMAC 作为查找键即可防止数据库泄露后被离线还原，同时支持"只输入密钥即可恢复"。

### 4.2 首次启动流程

```
App 首次启动
  │
  ├─ 1. 生成 device_uid 与设备密钥对（私钥存入安全硬件）
  ├─ 2. 读取邀请来源：APK 渠道信息 → 剪贴板口令（iOS 会弹出粘贴授权）
  ├─ 3. POST /v1/auth/register（请求体附带设备公钥，用设备私钥签名）
  │      服务端：IP 限流 → 黑名单检查
  │             → 创建 users / devices / device_credentials / subscriptions / user_balances
  │             → 生成账户号、账户密钥、邀请码
  │             → 邀请码合法则写入 invite_relations
  │             → 写 device_bind_logs(REGISTER)
  ├─ 4. 返回账户号、账户密钥（仅此一次）、令牌
  ├─ 5. 账户密钥备份页：显示密钥与二维码，提供"复制"和"保存为图片"
  │      勾选"我已保存到安全的地方"后继续；选择"稍后"则首页顶部持续显示备份提醒
  └─ 6. 进入首页（未开通套餐状态）
```

### 4.3 恢复账户与新设备登录

- 在引导页选择"恢复已有账户"，输入账户密钥或扫描迁移二维码（设置页生成，包含账户密钥，展示时需生物认证）。
- 服务端按 HMAC 查找账户，校验成功后为新设备生成 device_uid 与凭证，并写 `device_bind_logs(RESTORE)`。
- 设备数达到上限时，返回当前设备列表，用户需在本次恢复会话内先移除一台设备才能继续。
- 失败尝试限制：每 IP 每小时 10 次，超过后冷却 1 小时。
- 恢复成功后向该账户其他设备推送"有新设备登录"提醒，提醒中提供"不是我，立即重置密钥"入口。
- 同一台手机退出后登录另一个账户时，重新生成 device_uid 与设备密钥，避免设备记录跨账户复用。

### 4.4 重置账户密钥

用户在"账户与安全"中发起，需要生物认证与设备签名。服务端生成新密钥、`secret_version + 1`；除当前设备外，所有设备标记为 `REVOKED`，刷新令牌全部作废，凭证在下一次节点同步时被移除。新密钥只显示一次，并再次进入备份流程。

### 4.5 批量注册防护

- 注册本身不附带任何权益（后台可配置试用，默认关闭），从源头降低刷号动机；邀请奖励只在被邀请人付费后触发。
- IP 与 IP /24 前缀两级限流。
- 设备指纹哈希与黑名单比对。
- 可评估 iOS App Attest 与 Android 设备完整性判定作为风险信号（非商店分发下的可用性需在阶段二验证），只用于风险评分，不作为唯一拦截条件。
- 开启试用时，同一设备指纹只能领取一次。

## 5. 套餐与权益模型

### 5.1 套餐类型

| 类型 | 代码 | 说明 | 关键字段 |
|---|---|---|---|
| 时长套餐 | `TIME` | 按天或按月购买，期内可设置每 30 天流量配额或不限量 | 时长天数、周期配额、设备数、等级 |
| 流量包 | `TRAFFIC` | 固定流量，有效期内用完为止；可独立使用，无需时长套餐 | 流量大小、有效期、设备数、等级 |
| 设备加购 | `DEVICE_ADDON` | 在有效时长套餐上增加设备数，与套餐同时到期 | 增加设备数、每 30 天单价 |
| 余额充值 | 订单类型 `TOPUP` | 充值到余额，之后用余额购买套餐 | 充值金额 |

"按天"与"按月"都是 `TIME` 类型，只是时长不同（例如 1 天、7 天、30 天、90 天、365 天）。等级 `tier` 决定可用的节点组。

### 5.2 权益计算

```
可连接 = 账户状态正常 且 设备状态正常 且 (
           (时长套餐未过期 且 (周期配额为空 或 周期已用 < 周期配额))
           或 存在未过期且有剩余流量的流量包
         )

可用等级 = max(有效时长套餐等级, 有效流量包等级)
设备上限 = max(时长套餐设备数, 有效流量包设备数, 2) + 未过期的加购设备数之和
流量扣减 = 先扣时长套餐周期配额（不限量套餐不扣流量包）→ 再按到期时间从早到晚扣流量包
```

没有任何套餐时设备上限为 2，便于用户在多台设备上查看账户和充值，但不能连接。设备上限指可同时绑定的设备数。

### 5.3 叠加与变更规则

| 场景 | 规则 |
|---|---|
| 同等级续费 | 新到期时间 = max(当前时间, 原到期时间) + 套餐时长 |
| 跨等级变更（升级或降级） | 按剩余价值折算：剩余价值 = 剩余秒数 × 原套餐价格 ÷ 原套餐秒数；折算秒数 = 剩余价值 ÷ (新套餐价格 ÷ 新套餐秒数)；新到期时间 = 开通时刻 + 折算秒数 + 新套餐时长。报价时展示预估结果，开通时按实际剩余时间重新计算 |
| 周期流量配额 | 以开通时刻为锚点每 30 天重置已用量；跨等级变更时按新套餐配额开始新周期 |
| 流量包 | 每个流量包独立记录，互不合并；有效期从开通时刻计算；过期后剩余流量作废 |
| 设备加购 | 需要有效的时长套餐；价格 = 每 30 天单价 × 剩余天数 ÷ 30；与当时的套餐到期时间同时到期；续费套餐不会自动续加购 |
| 邀请奖励天数 | 有时长套餐时延长到期时间；没有时按后台配置的"奖励默认套餐"开通对应天数 |
| 到期或流量用尽 | 设备凭证在下一次节点同步时移除（10 秒级）；App 展示对应状态并引导续费 |
| 开通条件不满足 | 例如付款时主套餐已到期导致加购设备无法开通，订单金额转入余额并通知用户 |

**金额精度规则**：所有基础金额（套餐价格、折算与按天计价的结果）统一向上取整到 0.1 USDT。小数点后第 2 到第 4 位留给唯一尾数（见 6.2）。

### 5.4 示例

| 场景 | 计算 |
|---|---|
| 标准版剩 10 天，再买标准版 1 个月 | 到期时间延后 30 天 |
| 标准版（30 天 9.9 USDT）剩 15 天，升级高级版（30 天 19.9 USDT） | 剩余价值 4.95 USDT，折算高级版约 7.46 天；新到期 = 开通时刻 + 7.46 天 + 30 天；应付 19.9 USDT |
| 高级版剩 20 天，加购 1 台设备（每 30 天 2 USDT） | 2 × 20 ÷ 30 = 1.333…，向上取整为 1.4 USDT，加上唯一尾数后例如 1.4027 USDT |
| 持有不限量时长套餐时购买 100 GB 流量包（90 天有效） | 流量包在时长套餐有效期内不会被消耗，但有效期照常计算；购买前 App 需提示这一点 |

## 6. USDT-TRC20 充值

### 6.1 整体流程

```
[App]    选择套餐 → POST /v1/plans/quote → 得到 quote_id 与基础金额
[App]    确认订单 → POST /v1/orders（Idempotency-Key + 设备签名）
[API]    校验报价 → 选择收款地址 → 分配唯一尾数（写 amount_locks）→ 写 orders(PENDING)
[API]    返回收款地址与地址签名、应付金额、过期时间
[App]    校验地址签名 → 展示支付页 → 每 3 秒轮询订单状态
[用户]   从钱包或交易所转账
[Worker] 每 5 秒扫描收款地址的 USDT 转入 → 核验 → 写 chain_transfers(SEEN) → 订单置为 CONFIRMING
[Worker] 交易固化后执行到账事务：匹配订单 → 记账 → 开通权益 → 写 outbox
[App]    轮询到 COMPLETED → 结果页 → 首页刷新剩余时间
[Worker] 消费 outbox 事件 order.completed → 生成邀请奖励（冻结中）
```

余额支付（`pay_method = BALANCE`）不经过链上流程：在一个事务中扣减余额、写流水、开通权益，同步返回结果。

### 6.2 金额规则

**单位与精度**

TRC20 USDT 链上精度为 6 位小数。系统内部全部使用 micro-USDT 整数：`100.0043 USDT = 100_004_300`。接口中金额以字符串传输（例如 `"100.0043"`），避免客户端浮点误差。

**唯一尾数分配**

```
base = 报价基础金额（micro，必为 100_000 的整数倍，即 0.1 USDT 精度）

for attempt in 1..20:
    suffix = 安全随机数(1..999) × 100          # 0.0001 ~ 0.0999 USDT
    amount = base + suffix
    INSERT INTO amount_locks (receive_address_id, amount_micro, order_no, locked_until)
    VALUES ($addr, amount, $order_no, $expires_at + $cooldown)
    ON CONFLICT (receive_address_id, amount_micro) DO UPDATE
       SET order_no = EXCLUDED.order_no, locked_until = EXCLUDED.locked_until
     WHERE amount_locks.locked_until < now()
    RETURNING order_no
    → 返回行：分配成功
    → 无返回行：槽位被占用，继续尝试

全部失败 → 换下一个收款地址重试
所有地址都满 → 返回 50301（当前下单人数较多，请稍后再试）并触发扩容告警
```

尾数随机选取而非递增，避免他人根据金额猜测订单量。

**容量与有效期**

| 参数 | 默认值 | 说明 |
|---|---|---|
| 订单有效期 | 30 分钟 | 支付页倒计时 |
| 冷却期 | 2 小时（可配置） | 订单过期后金额继续锁定，用于识别迟到的付款，避免同一金额被分配给别人 |
| 每地址每价位槽位 | 999 个 | 一个地址在同一价位下每 2.5 小时约可承载 999 单 |
| 扩容方式 | 增加收款地址 | 容量与地址数量成正比 |

订单付款成功后，金额锁不提前释放，仍保持到"过期时间 + 冷却期"，这样同一金额的重复付款会进入异常队列，而不会被错误匹配给新订单。

### 6.3 链上核验规则

| 检查项 | 规则 |
|---|---|
| 合约地址 | 必须等于 USDT-TRC20 官方合约 `TR7NHqjeKQxGTCi8q8ZY4pL8otSzgjLj6t`（配置项，启动时校验）；同名假币一律忽略 |
| 事件 | `Transfer` 事件，`to` 等于我方某个 ACTIVE 或 PAUSED 状态的收款地址 |
| 执行结果 | 交易回执结果为 `SUCCESS`，失败交易记为 FAILED 不入账 |
| 金额 | 整数 micro-USDT，与订单应付金额精确相等 |
| 最小金额 | 低于 0.01 USDT 的转入不入库（过滤地址投毒） |
| 确认 | 所在区块已固化，才执行到账事务 |
| 唯一性 | `(network, tx_hash, event_index)` 全局唯一 |
| 时间 | 区块时间不早于订单创建时间减 2 分钟，防止用下单前的历史转账冒领 |
| 双源校验（阶段三） | TronGrid 与自建节点结果一致才入账 |

### 6.4 扫描策略

- 每个收款地址一个扫描游标（`chain_scan_cursors`），按区块时间递增扫描。
- 每次从"游标时间减 10 分钟"开始查询，重叠窗口防止遗漏，重复数据由唯一约束吸收。
- 两段式处理：未固化的交易写入 `SEEN`，订单显示"已检测到交易，等待区块确认"；固化后更新为 `SOLIDIFIED`，再执行到账事务。
- 只允许一个 worker 实例执行扫描，通过 PostgreSQL advisory lock 选主，其余实例待命。
- 数据源不可用超过 2 分钟告警；恢复后游标自动追赶。
- 阶段二使用 TronGrid 的账户 TRC20 交易查询接口（按收款地址、合约地址、起始时间过滤）并用交易回执接口二次核验，需配置 API Key 并遵守速率限制，具体参数以 TronGrid 官方文档为准。

### 6.5 订单状态机

```
             检测到匹配交易（未固化）        固化且核验通过
  PENDING ─────────────────────► CONFIRMING ─────────────► PAID ── 权益发放 ──► COMPLETED
    │  │                                                    ▲
    │  └── 用户取消 ──► CANCELLED ───┐                        │
    │                               ├── 冷却期内收到精确金额 ──┘
    └───── 超时 ─────► EXPIRED ─────┘
```

`fulfillment_result` 记录开通结果：`FULFILLED`（正常开通）或 `CREDITED_TO_BALANCE`（开通条件不满足，金额转入余额）。

### 6.6 到账事务

整个到账过程在一个数据库事务中完成，任一步失败全部回滚，由 worker 重试。

```sql
BEGIN;

-- ① 锁定链上转账记录：必须已固化且未处理
SELECT * FROM chain_transfers
 WHERE id = $transfer_id
   AND confirm_status = 'SOLIDIFIED'
   AND match_status   = 'UNPROCESSED'
 FOR UPDATE;
-- 无结果：已处理过或尚未固化，直接结束

-- ② 查找并锁定匹配订单
SELECT * FROM orders
 WHERE pay_method         = 'USDT_TRC20'
   AND receive_address_id = $receive_address_id
   AND pay_amount_micro   = $amount_micro
   AND created_at        <= $block_time + interval '2 minutes'
   AND (
         status IN ('PENDING', 'CONFIRMING')
      OR (status IN ('EXPIRED', 'CANCELLED') AND expires_at + $cooldown >= $block_time)
   )
 ORDER BY created_at DESC
 LIMIT 1
 FOR UPDATE;

-- ②-a 无匹配：写入异常队列后提交
INSERT INTO deposit_exceptions (chain_transfer_id, reason, suggested_order_id) VALUES (...);
UPDATE chain_transfers SET match_status = 'EXCEPTION', processed_at = now() WHERE id = $transfer_id;
COMMIT;

-- ③ 条件更新订单，影响行数必须为 1，否则回滚
UPDATE orders
   SET status = 'PAID',
       chain_transfer_id = $transfer_id,
       is_late_payment = (status IN ('EXPIRED', 'CANCELLED')),
       paid_at = now()
 WHERE id = $order_id
   AND status IN ('PENDING', 'CONFIRMING', 'EXPIRED', 'CANCELLED');

-- ④ 资金流水：先入账，再扣款（资金流向完整可追溯）
--    余额 +amount   idempotency_key = 'deposit:TRON:{tx_hash}:{event_index}'
--    余额 -amount   idempotency_key = 'purchase:order:{order_id}'   （仅 PLAN 订单）

-- ⑤ 发放权益：更新 subscriptions / traffic_packs / device_addons
--    写 subscription_ledger  idempotency_key = 'fulfill:order:{order_id}'
--    写 node_user_events（该用户所有设备凭证的最新可用等级）

-- ⑥ 收尾
UPDATE orders SET status = 'COMPLETED', fulfillment_result = 'FULFILLED', completed_at = now()
 WHERE id = $order_id AND status = 'PAID';
UPDATE chain_transfers SET match_status = 'MATCHED', order_id = $order_id, processed_at = now()
 WHERE id = $transfer_id;
INSERT INTO outbox_events (event_type, aggregate_type, aggregate_id, payload)
VALUES ('order.completed', 'order', $order_id, $payload);

COMMIT;
```

余额更新统一使用 `UPDATE user_balances SET available_micro = available_micro + $delta WHERE user_id = $uid AND available_micro + $delta >= 0 RETURNING available_micro`，再用返回值写入流水的 `balance_after_micro`。

### 6.7 异常场景

| 场景 | 系统行为 | 人工处理（后台） |
|---|---|---|
| 少付（例如交易所从到账数量中扣了手续费） | 无精确匹配，进入异常队列，并给出"疑似订单"（同一地址、金额差在 5% 以内、时间接近） | 关联订单开通（差额是否豁免由财务决定）或转入余额，L3 |
| 多付 | 同上 | 关联订单开通，多出部分转入余额，L3 |
| 冷却期之后才付款 | 同上 | 关联原订单或转入余额，L3 |
| 同一订单付了两次 | 第一笔入账，第二笔进入异常队列 | 转入余额，L3 |
| 只转了整数（例如 100） | 无匹配，进入异常队列 | 同少付 |
| 用下单之前的历史转账冒领 | 区块时间早于订单创建时间，不匹配，进入异常队列 | 驳回或转入余额 |
| 假 USDT、其他代币 | 合约地址不符，不入库，只计数监控 | 无 |
| 零金额、极小金额转账（地址投毒） | 低于 0.01 USDT 不入库 | 无；资金系统出款禁止从交易记录复制地址 |
| 交易执行失败 | 回执非 SUCCESS，记为 FAILED | 无 |
| 选错网络（ERC20、BEP20 等） | TRON 链上无记录，系统无法感知 | 支付页强提示仅支持 TRON 网络；TRON 地址格式与 EVM 地址不兼容，多数钱包会直接拦截 |
| 开通条件不满足 | 金额转入余额，订单结果为 CREDITED_TO_BALANCE，通知用户 | 无 |

### 6.8 收款地址防篡改

收款地址是整个系统最值得攻击的数据：只要换掉一个地址，所有新订单的钱都会流向攻击者。防护措施如下。

1. 资金系统用离线 Ed25519 密钥对 `yuhai-addr-v1|TRON|{地址}|{有效期截止 Unix 时间}` 签名。业务系统只能导入已签名的地址，自身无法生成有效签名。
2. App 内置签名公钥（同时内置两把以支持轮换）。展示地址前校验签名和有效期，校验失败时不展示地址，提示"支付通道校验失败，请更新 App 或联系客服"。
3. 后台导入或启用地址需要二级验证与双人复核，并立即通知全部管理员与资金负责人。
4. worker 启动时及每小时比对一次收款地址列表与资金系统公布的清单，不一致立即告警并暂停下单。

### 6.9 阶段一模拟到账

- 后台订单详情页提供"模拟到账"按钮，支持五种场景：精确金额、少付、多付、重复支付、超时后支付。
- 点击后生成 `network = MOCK` 的 `chain_transfers` 记录（`tx_hash` 以 `mock_` 开头），先写入 `SEEN`，3 秒后更新为 `SOLIDIFIED`，然后调用与生产完全相同的到账事务。
- 生产构建通过 Go build tag 排除模拟接口；服务启动时如果在生产环境发现 MOCK 网络的收款地址或转账记录，直接拒绝启动。

### 6.10 链上数据源接口

```go
// TransferEvent 统一描述一笔 TRC20 转入，真实链与模拟数据源共用
type TransferEvent struct {
	Network     string    // "TRON" | "MOCK"
	TxHash      string
	EventIndex  int
	Contract    string
	From        string
	To          string
	AmountMicro int64     // 1 USDT = 1_000_000
	BlockNumber int64
	BlockTime   time.Time
	Solidified  bool
	Success     bool      // 交易回执结果
}

// ChainSource 只读链上数据源：TronGrid、自建节点或模拟源
type ChainSource interface {
	Name() string
	ListIncoming(ctx context.Context, address string, since time.Time) ([]TransferEvent, error)
	GetTransfers(ctx context.Context, txHash string) ([]TransferEvent, error) // 二次核验
}

// DepositService 与数据源无关，阶段一与生产共用
type DepositService interface {
	Ingest(ctx context.Context, ev TransferEvent) error     // 核验并落库，幂等
	Settle(ctx context.Context, transferID int64) error     // 固化后执行到账事务，幂等
}
```

## 7. 邀请体系

### 7.1 邀请码与链接

- 邀请码：6 位，字符集为 `23456789ABCDEFGHJKMNPQRSTUVWXYZ`（去掉 0、1、I、L、O），约 8.9 亿种组合，注册时生成，全局唯一。
- 渠道码：后台可为推广合作方创建 4 到 12 位自定义邀请码，便于统计渠道效果。
- 邀请链接：`https://{官网域名}/i/K7M3QX`。

邀请落地页流程：

```
打开 /i/K7M3QX
 ├─ 页面展示邀请码与"复制邀请码并下载"按钮
 │    点击时写入剪贴板：宇海邀请码 K7M3QX
 ├─ Android：下载写入了邀请码的安装包（/download/android?c=K7M3QX）
 └─ iOS：进入安装指引页（TestFlight 公开链接），剪贴板中已带有邀请码
```

### 7.2 归因方式

| 优先级 | 方式 | 平台 | 可靠性 | 说明 |
|---|---|---|---|---|
| 1 | APK 签名块写入邀请码 | Android | 高 | 在 APK Signing Block 的自定义区域写入渠道信息，不改动已签名内容、无需重新签名（与 Walle、VasDolly 原理相同）。渠道包按邀请码生成后缓存到对象存储，发版时批量失效；发布流程必须用 `apksigner verify` 校验 v2/v3 签名 |
| 2 | 剪贴板口令 | 双端 | 中 | App 首次启动读取形如"宇海邀请码 XXXXXX"的内容；iOS 会弹出粘贴授权，用户拒绝则跳过；读取后立即清空该口令 |
| 3 | 手动输入 | 双端 | 高 | 注册后 72 小时内、首次付费前可在邀请页输入 |
| 不采用 | IP 与 UA 指纹匹配 | 双端 | 低 | 误判率高，且需要收集额外数据，与隐私定位冲突 |

### 7.3 绑定规则

- 每个用户只能绑定一次邀请人，绑定后不可修改（`invite_relations` 以被邀请人为主键）。
- 绑定窗口：注册后 72 小时内，且在首次付费之前。
- 不能绑定自己；不能互相邀请（A 已邀请 B，则 B 不能成为 A 的邀请人）。
- 只记录一级关系，不做多级返利。
- 命中黑名单的邀请码或账户不能绑定。

### 7.4 奖励规则

| 触发事件 | 说明 | 建议 |
|---|---|---|
| `INVITEE_FIRST_PAID` | 被邀请人首笔付费订单完成 | 默认主规则 |
| `INVITEE_PAID` | 被邀请人每笔付费订单完成，可按比例奖励余额 | 可选，需设置单个邀请人上限 |
| `INVITEE_REGISTERED` | 被邀请人完成注册 | 不建议；如开启，奖励应很小且冻结期更长 |

奖励类型：天数（`DAYS`）、流量（`TRAFFIC`）、余额（`BALANCE`）。受益人可以是邀请人或被邀请人，每条规则单独配置。

默认配置示例：被邀请人首单完成后，邀请人获得 7 天，被邀请人额外获得 3 天，冻结 72 小时后发放。

### 7.5 奖励生命周期

```
order.completed 事件
   │
   ▼
检查：存在邀请关系 → 规则生效 → 满足最低订单金额 → 风控检查
   │
   ├─ 通过 ─────► PENDING（release_at = 当前时间 + 冻结时长）
   ├─ 可疑 ─────► REVIEW（等待人工审核）
   └─ 明确作弊 ──► CANCELLED
                     
PENDING ── 到达 release_at，再次校验通过 ──► RELEASED（写权益或余额流水）
PENDING ── 冻结期内订单被判定异常或命中黑名单 ──► CANCELLED
REVIEW  ── 人工通过 ──► PENDING / 人工驳回 ──► CANCELLED
```

生成奖励时依靠唯一约束 `(rule_id, beneficiary_user_id, invitee_user_id, trigger_ref)` 保证同一事件只生成一次；发放时流水幂等键为 `invite_reward:{reward_id}`。释放任务每分钟执行，使用 `FOR UPDATE SKIP LOCKED` 分批处理。

### 7.6 防刷规则

| 信号 | 判定 | 处理 |
|---|---|---|
| 设备指纹相同 | 邀请人与被邀请人存在相同的设备指纹哈希 | 作废 |
| 付款来源地址相同 | 被邀请人付款的 `from_address` 与邀请人任一历史付款地址相同，且该地址不在"公共地址"列表中 | 转人工审核 |
| 网络接近 | 双方注册 IP /24 前缀哈希相同，且注册时间相差不到 1 小时 | 转人工审核 |
| 频率异常 | 单个邀请人 24 小时内奖励数超过阈值 | 超出部分转人工审核并告警 |
| 黑名单 | 任一方命中黑名单 | 作废 |
| 订单异常 | 被邀请人订单在冻结期内被判定异常 | 作废 |

交易所热钱包地址会被大量用户共用。系统维护"公共地址"列表：同一付款地址出现在多个无邀请关系的账户中时自动标记为公共地址，不再作为自邀判定依据。

## 8. 节点与流量

### 8.1 节点模型

- **节点组**：设定最低可用等级 `min_tier`，用户等级不低于该值才能看到并使用组内节点。
- **节点**：一台服务器，包含地区、城市、状态、负载、容量。
- **入站**：节点上的一个协议端口（例如 VLESS-Reality 443、WireGuard 51820）。一个节点可以有多个入站。

App 以节点为单位展示，协议由客户端自动选择，用户也可以在连接设置中设定偏好。

### 8.2 凭证模型

每台设备一套独立凭证，而不是每个账户一套。这样移除设备可以立即在节点侧失效，流量可以按设备统计，设备上限也能在服务端强制执行。

| 协议 | 凭证 | 生成方 | 存储 |
|---|---|---|---|
| VLESS | 每设备一个 UUID | 服务端 | 明文（本身不是密码，需配合 Reality 参数使用） |
| Trojan | 每设备一个随机口令 | 服务端 | AES-256-GCM 加密 |
| Shadowsocks 2022 | 每设备一个用户密钥（多用户模式） | 服务端 | AES-256-GCM 加密 |
| WireGuard | 每设备一对密钥 | 客户端生成，只上传公钥 | 仅公钥；服务端分配隧道内地址 |

Reality 私钥与 WireGuard 服务端私钥在节点本地生成，只向控制面上报公钥，控制面数据库中不存在任何节点私钥。

### 8.3 node-agent 工作流程

```
首次部署
 └─ 使用后台生成的一次性注册令牌（24 小时有效）调用 /node/v1/enroll
    提交 CSR、Reality 公钥、WireGuard 公钥 → 获得 mTLS 客户端证书

启动
 └─ 拉取全量用户快照 → 写入 Xray（gRPC API）与 WireGuard（wg set）

运行循环
 ├─ 每 10 秒：拉取增量用户变更 → 增删 Xray 用户 / WireGuard peer
 ├─ 每 30 秒：心跳（CPU、内存、带宽、连接数、内核版本、配置版本）
 ├─ 每 60 秒：读取并清零每用户流量计数 → 先写本地磁盘 → 上报（附 report_id）
 │            上报失败时保留本地数据，用同一 report_id 重试
 └─ 每 30 分钟：全量快照校验，校验和不一致则重建
```

Xray 按用户统计流量依赖用户的 email 字段，统一使用凭证 ID 作为该字段值，不包含任何用户可识别信息。

### 8.4 增量同步

`node_user_events` 记录每个凭证的最新"可用等级"（0 表示当前不可连接）。节点按 `effective_tier >= 所在组 min_tier` 决定该凭证应当存在还是移除，所有操作都是幂等的"设置为目标状态"。

由于并发事务的提交顺序可能与自增 ID 顺序不一致，agent 每次从"上次游标减 200"开始读取（重叠窗口），并依靠每 30 分钟的全量校验兜底。

### 8.5 流量统计

```
POST /node/v1/traffic { report_id, period_start, period_end, items: [{credential_id, up, down}] }

事务：
  INSERT INTO traffic_reports (node_id, report_id, ...)      -- 冲突说明已处理过，直接返回成功
  按 credential 找到 device 与 user
  UPSERT traffic_daily：上下行字节累加
  扣减权益：周期配额 → 流量包（按到期时间顺序）
  若本次扣减导致不可连接 → 写 node_user_events(effective_tier = 0, reason = 'QUOTA')
```

- 流量统计存在最多约 1 分钟的延迟，允许少量超用，套餐说明中需注明。
- 节点和用户规模变大后，先写入 Redis Stream，由 worker 每分钟批量聚合入库；阶段三可迁移到 TimescaleDB 或 ClickHouse。
- `traffic_daily` 按月分区，保留 180 天，之后汇总为月度数据。

### 8.6 到期处理

worker 每分钟扫描到期的时长套餐、过期的流量包与加购设备：写入 `subscription_ledger(EXPIRE)`（幂等键 `expire:{user_id}:{到期时间戳}`），重新计算用户可用等级，并为其全部设备写入 `node_user_events`。

### 8.7 节点健康

- 被动检测：超过 90 秒未收到心跳即标记为 OFFLINE，App 节点列表中显示为不可用。
- 主动探测：控制面从至少 2 个位置每 30 秒探测节点端口，连续 3 次失败告警。
- 负载分：`load = max(CPU 占用率, 带宽占用率, 连接数 ÷ 容量)`，下发给客户端参与选点。
- 维护模式：设置为 MAINTENANCE 后不再参与自动选择，已连接用户在下一次重连时迁移。

### 8.8 节点隐私配置

- Xray 关闭访问日志（access log），错误日志级别设为 warning 且不输出目标地址。
- 不部署流量镜像、深度包检测或任何记录访问目标的组件。
- 系统层不持久化连接跟踪日志。
- 节点磁盘上不保存任何用户流量内容；WireGuard 本身不记录连接日志。

## 9. 页面设计

### 9.1 视觉方向：深海荧光

"宇"与"海"都指向广阔、深邃、安静。视觉取材于深海：光照不到的地方很暗，但不是纯黑，而是带着蓝色的深水；深海里真正发光的只有生物荧光，它少量、柔和，只在有生命的时候出现。

对应到产品：界面整体安静深沉，荧光色只在"已连接、受保护"时出现。用户不读文字，也能从颜色判断自己是否处于保护之中。

**取舍说明**（为避免模板感而刻意做出的选择）

- 不用中性黑或灰黑背景，也不用 VPN 类产品最常见的霓虹蓝紫渐变与满屏发光。背景是带蓝色的深水色。
- 荧光色不作为品牌装饰色到处使用，只承担"受保护"这一个含义，所以它出现时才有分量。

### 9.5 连接按钮：潮汐环

- **结构**：外环（2 pt 描边）+ 环内圆形"水体"区域 + 中心文字。直径约为屏幕宽度的 56%。
- **未连接**：礁色描边，环内为静止的深色水面。
- **正在连接**：水位在 1.2 秒内从底部升到 70%（ease-in-out），荧光色透明度从 0 渐入到 60%；若连接耗时更长，水位在 70% 处轻微起伏等待。
- **已连接**：水位满，水面是振幅 3 pt、周期 4 秒的缓慢起伏，外环描边变为荧光色。只在环内有柔和光感，不做外发光、不加粒子。
- **正在重新连接**：水面静止，外环变为缓慢旋转的虚线。
- **断开**：水位在 400 ms 内回落，颜色回到礁色。
- **连接失败**：外环闪一次珊瑚色后回到未连接。
- **实现**：Flutter `CustomPainter` + `Ticker`；水面由两条相位差 π/2 的正弦曲线叠加；单帧绘制耗时目标小于 2 ms；App 进入后台时暂停动画。

## 10. 数据库设计

### 10.1 约定

| 项 | 约定 |
|---|---|
| 数据库 | PostgreSQL 17 及以上，UTF-8，时间一律 `TIMESTAMPTZ`（UTC） |
| 主键 | `BIGINT GENERATED ALWAYS AS IDENTITY`；对外暴露的编号（订单号、账户号）使用独立的不可猜测字段 |
| 金额 | `*_micro BIGINT`，1 USDT = 1,000,000 |
| 流量 | 字节，`BIGINT` |
| 枚举 | `TEXT + CHECK`，便于迁移时增加取值 |
| 敏感字段 | 应用层 AES-256-GCM 加密，列名以 `_enc` 结尾，密钥来自 KMS |
| 流水表 | 只追加：触发器禁止 UPDATE / DELETE，应用数据库角色不授予 UPDATE / DELETE / TRUNCATE 权限 |
| 幂等 | 所有流水表带 `idempotency_key UNIQUE`，键由业务确定性构造（见 12.3） |

### 10.2 实体关系概览

### 10.3 表结构（DDL）

```sql
-- =====================================================================
-- 宇海加密VPN 数据库结构 v1
-- 金额 *_micro：1 USDT = 1,000,000；流量单位：字节；时间：UTC
-- =====================================================================

CREATE EXTENSION IF NOT EXISTS pgcrypto;

-- 只追加表保护
CREATE OR REPLACE FUNCTION forbid_mutation() RETURNS trigger
LANGUAGE plpgsql AS $$
BEGIN
  RAISE EXCEPTION '表 % 只允许追加，禁止 %', TG_TABLE_NAME, TG_OP;
END $$;

-- =====================================================================
-- 1. 用户、设备、认证
-- =====================================================================

CREATE TABLE users (
  id                       BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  account_no               VARCHAR(10)  NOT NULL UNIQUE,
  secret_lookup            CHAR(64)     NOT NULL UNIQUE,     -- HMAC-SHA256(pepper, 账户密钥)
  secret_version           INT          NOT NULL DEFAULT 1,
  invite_code              VARCHAR(12)  NOT NULL UNIQUE,
  status                   TEXT         NOT NULL DEFAULT 'ACTIVE'
                           CHECK (status IN ('ACTIVE', 'SUSPENDED', 'BANNED')),
  risk_flags               JSONB        NOT NULL DEFAULT '[]',
  register_channel         VARCHAR(32),
  register_ip_hash         CHAR(64),                          -- 30 天后由任务置空
  register_ip_prefix_hash  CHAR(64),                          -- /24 前缀哈希，30 天后置空
  created_at               TIMESTAMPTZ  NOT NULL DEFAULT now(),
  updated_at               TIMESTAMPTZ  NOT NULL DEFAULT now()
);

CREATE TABLE devices (
  id                BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id           BIGINT       NOT NULL REFERENCES users(id),
  device_uid        UUID         NOT NULL UNIQUE,
  pubkey            TEXT         NOT NULL,                    -- P-256 公钥（SPKI Base64）
  platform          TEXT         NOT NULL CHECK (platform IN ('ANDROID', 'IOS')),
  model             VARCHAR(64),
  os_version        VARCHAR(32),
  app_version       VARCHAR(32),
  fingerprint_hash  CHAR(64),                                 -- 仅用于风控比对
  display_name      VARCHAR(64),
  status            TEXT         NOT NULL DEFAULT 'ACTIVE' CHECK (status IN ('ACTIVE', 'REVOKED')),
  last_seen_at      TIMESTAMPTZ,
  created_at        TIMESTAMPTZ  NOT NULL DEFAULT now(),
  revoked_at        TIMESTAMPTZ
);
CREATE INDEX idx_devices_user_active ON devices (user_id) WHERE status = 'ACTIVE';
CREATE INDEX idx_devices_fingerprint ON devices (fingerprint_hash);

CREATE TABLE device_credentials (
  id                BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  device_id         BIGINT       NOT NULL UNIQUE REFERENCES devices(id),
  proxy_uuid        UUID         NOT NULL UNIQUE,             -- VLESS
  proxy_secret_enc  BYTEA        NOT NULL,                    -- Trojan / SS-2022 口令（加密）
  wg_pubkey         VARCHAR(64)  UNIQUE,                      -- 设备上传；私钥不离开设备
  wg_address        INET         UNIQUE,                      -- 隧道内地址，全局分配
  status            TEXT         NOT NULL DEFAULT 'ACTIVE' CHECK (status IN ('ACTIVE', 'REVOKED')),
  rotated_at        TIMESTAMPTZ,
  created_at        TIMESTAMPTZ  NOT NULL DEFAULT now()
);

CREATE TABLE device_bind_logs (
  id               BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id          BIGINT       NOT NULL,
  device_id        BIGINT       NOT NULL,
  action           TEXT         NOT NULL CHECK (action IN (
                     'REGISTER', 'RESTORE', 'REVOKE_BY_USER', 'REVOKE_BY_ADMIN',
                     'REVOKE_BY_SECRET_RESET', 'CREDENTIAL_ROTATE')),
  operator_type    TEXT         NOT NULL CHECK (operator_type IN ('USER', 'ADMIN', 'SYSTEM')),
  operator_id      BIGINT,
  ip_hash          CHAR(64),
  detail           JSONB        NOT NULL DEFAULT '{}',
  idempotency_key  VARCHAR(128) NOT NULL UNIQUE,
  created_at       TIMESTAMPTZ  NOT NULL DEFAULT now()
);
CREATE INDEX idx_device_bind_logs_user ON device_bind_logs (user_id, created_at DESC);
CREATE TRIGGER trg_device_bind_logs_append_only BEFORE UPDATE OR DELETE ON device_bind_logs
  FOR EACH ROW EXECUTE FUNCTION forbid_mutation();

CREATE TABLE auth_sessions (
  id              BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id         BIGINT       NOT NULL REFERENCES users(id),
  device_id       BIGINT       NOT NULL REFERENCES devices(id),
  refresh_hash    CHAR(64)     NOT NULL UNIQUE,               -- SHA-256(refresh_token)
  family_id       UUID         NOT NULL,                      -- 同一登录的令牌族；检测到旧令牌重放则整族作废
  secret_version  INT          NOT NULL,
  expires_at      TIMESTAMPTZ  NOT NULL,
  rotated_at      TIMESTAMPTZ,
  revoked_at      TIMESTAMPTZ,
  created_at      TIMESTAMPTZ  NOT NULL DEFAULT now()
);
CREATE INDEX idx_auth_sessions_family ON auth_sessions (family_id);

-- =====================================================================
-- 2. 套餐与权益
-- =====================================================================

CREATE TABLE plans (
  id                  BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  code                VARCHAR(32)  NOT NULL UNIQUE,
  name                VARCHAR(64)  NOT NULL,
  plan_type           TEXT         NOT NULL CHECK (plan_type IN ('TIME', 'TRAFFIC', 'DEVICE_ADDON')),
  tier                SMALLINT     NOT NULL DEFAULT 1 CHECK (tier BETWEEN 1 AND 9),
  duration_days       INT,                                    -- TIME
  period_quota_bytes  BIGINT,                                 -- TIME：每 30 天配额，NULL 表示不限
  pack_bytes          BIGINT,                                 -- TRAFFIC
  validity_days       INT,                                    -- TRAFFIC
  device_limit        INT,                                    -- TIME / TRAFFIC
  extra_devices       INT,                                    -- DEVICE_ADDON
  price_micro         BIGINT       NOT NULL
                      CHECK (price_micro > 0 AND price_micro % 100000 = 0),   -- 0.1 USDT 精度
  display_config      JSONB        NOT NULL DEFAULT '{}',     -- 角标、描述、分组
  sort_order          INT          NOT NULL DEFAULT 0,
  status              TEXT         NOT NULL DEFAULT 'DRAFT'
                      CHECK (status IN ('DRAFT', 'ON_SALE', 'OFF_SALE')),
  version             INT          NOT NULL DEFAULT 1,        -- 改价或改配置时 +1
  created_at          TIMESTAMPTZ  NOT NULL DEFAULT now(),
  updated_at          TIMESTAMPTZ  NOT NULL DEFAULT now(),
  CONSTRAINT chk_plan_shape CHECK (
       (plan_type = 'TIME'         AND duration_days > 0 AND device_limit > 0)
    OR (plan_type = 'TRAFFIC'      AND pack_bytes > 0 AND validity_days > 0 AND device_limit > 0)
    OR (plan_type = 'DEVICE_ADDON' AND extra_devices > 0)
  )
);

CREATE TABLE subscriptions (
  user_id             BIGINT       PRIMARY KEY REFERENCES users(id),
  plan_id             BIGINT       REFERENCES plans(id),
  tier                SMALLINT     NOT NULL DEFAULT 0,        -- 0 表示没有有效时长套餐
  started_at          TIMESTAMPTZ,
  expire_at           TIMESTAMPTZ,
  device_limit        INT          NOT NULL DEFAULT 0,
  period_quota_bytes  BIGINT,
  period_used_bytes   BIGINT       NOT NULL DEFAULT 0 CHECK (period_used_bytes >= 0),
  period_reset_at     TIMESTAMPTZ,
  version             BIGINT       NOT NULL DEFAULT 0,
  updated_at          TIMESTAMPTZ  NOT NULL DEFAULT now()
);
CREATE INDEX idx_subscriptions_expire ON subscriptions (expire_at) WHERE tier > 0;

CREATE TABLE traffic_packs (
  id            BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id       BIGINT       NOT NULL REFERENCES users(id),
  tier          SMALLINT     NOT NULL,
  device_limit  INT          NOT NULL,
  total_bytes   BIGINT       NOT NULL CHECK (total_bytes > 0),
  used_bytes    BIGINT       NOT NULL DEFAULT 0 CHECK (used_bytes >= 0),
  expire_at     TIMESTAMPTZ  NOT NULL,
  source_type   TEXT         NOT NULL CHECK (source_type IN ('ORDER', 'INVITE_REWARD', 'ADMIN')),
  source_id     BIGINT       NOT NULL,
  status        TEXT         NOT NULL DEFAULT 'ACTIVE'
                CHECK (status IN ('ACTIVE', 'EXHAUSTED', 'EXPIRED')),
  created_at    TIMESTAMPTZ  NOT NULL DEFAULT now(),
  UNIQUE (source_type, source_id)
);
CREATE INDEX idx_traffic_packs_user_active ON traffic_packs (user_id, expire_at) WHERE status = 'ACTIVE';

CREATE TABLE device_addons (
  id           BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id      BIGINT       NOT NULL REFERENCES users(id),
  quantity     INT          NOT NULL CHECK (quantity > 0),
  expire_at    TIMESTAMPTZ  NOT NULL,
  source_type  TEXT         NOT NULL CHECK (source_type IN ('ORDER', 'ADMIN')),
  source_id    BIGINT       NOT NULL,
  created_at   TIMESTAMPTZ  NOT NULL DEFAULT now(),
  UNIQUE (source_type, source_id)
);
CREATE INDEX idx_device_addons_user ON device_addons (user_id, expire_at);

CREATE TABLE subscription_ledger (
  id                   BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id              BIGINT       NOT NULL REFERENCES users(id),
  change_type          TEXT         NOT NULL CHECK (change_type IN (
                         'PURCHASE', 'RENEW', 'TIER_CHANGE', 'TRAFFIC_PACK', 'DEVICE_ADDON',
                         'INVITE_REWARD', 'ADMIN_ADJUST', 'TRAFFIC_CONSUME_OVERFLOW',
                         'PERIOD_RESET', 'EXPIRE', 'REVOKE')),
  source_type          TEXT         NOT NULL CHECK (source_type IN ('ORDER', 'INVITE_REWARD', 'ADMIN_APPROVAL', 'SYSTEM')),
  source_id            BIGINT,
  delta_seconds        BIGINT       NOT NULL DEFAULT 0,
  delta_bytes          BIGINT       NOT NULL DEFAULT 0,
  delta_devices        INT          NOT NULL DEFAULT 0,
  before_snapshot      JSONB        NOT NULL,
  after_snapshot       JSONB        NOT NULL,
  idempotency_key      VARCHAR(128) NOT NULL UNIQUE,
  operator_type        TEXT         NOT NULL CHECK (operator_type IN ('USER', 'ADMIN', 'SYSTEM')),
  operator_id          BIGINT,
  remark               VARCHAR(255),
  created_at           TIMESTAMPTZ  NOT NULL DEFAULT now()
);
CREATE INDEX idx_subscription_ledger_user ON subscription_ledger (user_id, created_at DESC);
CREATE TRIGGER trg_subscription_ledger_append_only BEFORE UPDATE OR DELETE ON subscription_ledger
  FOR EACH ROW EXECUTE FUNCTION forbid_mutation();

CREATE TABLE user_balances (
  user_id          BIGINT       PRIMARY KEY REFERENCES users(id),
  available_micro  BIGINT       NOT NULL DEFAULT 0 CHECK (available_micro >= 0),
  version          BIGINT       NOT NULL DEFAULT 0,
  updated_at       TIMESTAMPTZ  NOT NULL DEFAULT now()
);

CREATE TABLE balance_ledger (
  id                   BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id              BIGINT       NOT NULL REFERENCES users(id),
  entry_type           TEXT         NOT NULL CHECK (entry_type IN (
                         'DEPOSIT', 'PURCHASE', 'INVITE_REWARD', 'EXCEPTION_CREDIT',

  balance_after_micro  BIGINT       NOT NULL CHECK (balance_after_micro >= 0),
  source_type          TEXT         NOT NULL CHECK (source_type IN (
                         'CHAIN_TRANSFER', 'ORDER', 'INVITE_REWARD', 'DEPOSIT_EXCEPTION', 'ADMIN_APPROVAL')),
  source_id            BIGINT       NOT NULL,
  idempotency_key      VARCHAR(128) NOT NULL UNIQUE,
  operator_type        TEXT         NOT NULL CHECK (operator_type IN ('USER', 'ADMIN', 'SYSTEM')),
  operator_id          BIGINT,
  remark               VARCHAR(255),
  created_at           TIMESTAMPTZ  NOT NULL DEFAULT now()
);
CREATE INDEX idx_balance_ledger_user ON balance_ledger (user_id, created_at DESC);
CREATE TRIGGER trg_balance_ledger_append_only BEFORE UPDATE OR DELETE ON balance_ledger
  FOR EACH ROW EXECUTE FUNCTION forbid_mutation();

-- 4. 订单与充值

CREATE TABLE receive_addresses (
  id            BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  network       TEXT         NOT NULL CHECK (network IN ('TRON', 'MOCK')),
  address       VARCHAR(64)  NOT NULL UNIQUE,
  label         VARCHAR(64),
  signature     TEXT         NOT NULL,        -- 资金系统离线密钥签名
  sig_key_id    VARCHAR(32)  NOT NULL,
  valid_until   TIMESTAMPTZ  NOT NULL,
  status        TEXT         NOT NULL DEFAULT 'PAUSED' CHECK (status IN ('ACTIVE', 'PAUSED', 'RETIRED')),
  approval_id   BIGINT,                        -- 导入审批单
  created_at    TIMESTAMPTZ  NOT NULL DEFAULT now(),
  updated_at    TIMESTAMPTZ  NOT NULL DEFAULT now()
);

CREATE TABLE plan_quotes (
  id                 UUID         PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id            BIGINT       NOT NULL REFERENCES users(id),
  plan_id            BIGINT       NOT NULL REFERENCES plans(id),
  plan_version       INT          NOT NULL,
  base_amount_micro  BIGINT       NOT NULL CHECK (base_amount_micro > 0 AND base_amount_micro % 100000 = 0),
  detail             JSONB        NOT NULL,     -- 折算、按天计价明细、预估新到期时间
  expires_at         TIMESTAMPTZ  NOT NULL,     -- 10 分钟
  used_by_order_id   BIGINT       UNIQUE,
  created_at         TIMESTAMPTZ  NOT NULL DEFAULT now()
);

CREATE TABLE orders (
  id                  BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  order_no            VARCHAR(24)  NOT NULL UNIQUE,
  user_id             BIGINT       NOT NULL REFERENCES users(id),
  order_type          TEXT         NOT NULL CHECK (order_type IN ('PLAN', 'TOPUP')),
  plan_id             BIGINT       REFERENCES plans(id),
  quote_id            UUID         REFERENCES plan_quotes(id),
  plan_snapshot       JSONB,                    -- 下单时的套餐完整快照
  base_amount_micro   BIGINT       NOT NULL CHECK (base_amount_micro > 0),
  pay_amount_micro    BIGINT       NOT NULL,
  pay_method          TEXT         NOT NULL CHECK (pay_method IN ('USDT_TRC20', 'BALANCE')),
  receive_address_id  BIGINT       REFERENCES receive_addresses(id),
  status              TEXT         NOT NULL DEFAULT 'PENDING' CHECK (status IN (
                        'PENDING', 'CONFIRMING', 'PAID', 'COMPLETED', 'EXPIRED', 'CANCELLED')),
  fulfillment_result  TEXT         CHECK (fulfillment_result IN ('FULFILLED', 'CREDITED_TO_BALANCE')),
  chain_transfer_id   BIGINT       UNIQUE,      -- 一笔链上转账只能对应一个订单
  is_late_payment     BOOLEAN      NOT NULL DEFAULT false,
  client_idem_key     VARCHAR(64)  NOT NULL,
  expires_at          TIMESTAMPTZ  NOT NULL,
  paid_at             TIMESTAMPTZ,
  completed_at        TIMESTAMPTZ,
  created_at          TIMESTAMPTZ  NOT NULL DEFAULT now(),
  updated_at          TIMESTAMPTZ  NOT NULL DEFAULT now(),
  UNIQUE (user_id, client_idem_key),
  CHECK (pay_amount_micro >= base_amount_micro),
  CHECK (order_type <> 'PLAN'  OR plan_id IS NOT NULL),
  CHECK (order_type <> 'TOPUP' OR pay_method = 'USDT_TRC20'),
  CHECK (pay_method <> 'USDT_TRC20' OR receive_address_id IS NOT NULL)
);
CREATE INDEX idx_orders_match   ON orders (receive_address_id, pay_amount_micro, created_at DESC)
  WHERE pay_method = 'USDT_TRC20';
CREATE INDEX idx_orders_user    ON orders (user_id, created_at DESC);
CREATE INDEX idx_orders_pending ON orders (expires_at) WHERE status IN ('PENDING', 'CONFIRMING');

CREATE TABLE amount_locks (
  receive_address_id  BIGINT       NOT NULL REFERENCES receive_addresses(id),
  amount_micro        BIGINT       NOT NULL,
  order_no            VARCHAR(24)  NOT NULL,
  locked_until        TIMESTAMPTZ  NOT NULL,     -- 订单过期时间 + 冷却期
  PRIMARY KEY (receive_address_id, amount_micro)
);

CREATE TABLE chain_transfers (
  id                  BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  network             TEXT         NOT NULL CHECK (network IN ('TRON', 'MOCK')),
  tx_hash             VARCHAR(80)  NOT NULL,
  event_index         INT          NOT NULL DEFAULT 0,
  contract_address    VARCHAR(64)  NOT NULL,
  from_address        VARCHAR(64)  NOT NULL,
  to_address          VARCHAR(64)  NOT NULL,
  receive_address_id  BIGINT       NOT NULL REFERENCES receive_addresses(id),
  amount_micro        BIGINT       NOT NULL CHECK (amount_micro > 0),
  block_number        BIGINT       NOT NULL,
  block_time          TIMESTAMPTZ  NOT NULL,
  confirm_status      TEXT         NOT NULL CHECK (confirm_status IN ('SEEN', 'SOLIDIFIED', 'FAILED')),
  match_status        TEXT         NOT NULL DEFAULT 'UNPROCESSED'
                      CHECK (match_status IN ('UNPROCESSED', 'MATCHED', 'EXCEPTION')),
  order_id            BIGINT       UNIQUE REFERENCES orders(id),
  data_source         VARCHAR(32)  NOT NULL,     -- TRONGRID / FULLNODE / MOCK
  raw                 JSONB,
  created_at          TIMESTAMPTZ  NOT NULL DEFAULT now(),
  processed_at        TIMESTAMPTZ,
  UNIQUE (network, tx_hash, event_index)
);
CREATE INDEX idx_chain_transfers_todo ON chain_transfers (created_at)
  WHERE match_status = 'UNPROCESSED' AND confirm_status = 'SOLIDIFIED';
CREATE INDEX idx_chain_transfers_from ON chain_transfers (from_address);
CREATE TRIGGER trg_chain_transfers_no_delete BEFORE DELETE ON chain_transfers
  FOR EACH ROW EXECUTE FUNCTION forbid_mutation();

ALTER TABLE orders ADD CONSTRAINT fk_orders_chain_transfer
  FOREIGN KEY (chain_transfer_id) REFERENCES chain_transfers(id);

CREATE TABLE chain_scan_cursors (
  receive_address_id  BIGINT       PRIMARY KEY REFERENCES receive_addresses(id),
  last_block_time     TIMESTAMPTZ  NOT NULL,
  last_block_number   BIGINT,
  last_success_at     TIMESTAMPTZ,
  updated_at          TIMESTAMPTZ  NOT NULL DEFAULT now()
);

CREATE TABLE deposit_exceptions (
  id                  BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  chain_transfer_id   BIGINT       NOT NULL UNIQUE REFERENCES chain_transfers(id),
  reason              TEXT         NOT NULL CHECK (reason IN (
                        'AMOUNT_MISMATCH', 'NO_MATCHING_ORDER', 'LATE_BEYOND_COOLDOWN',
                        'DUPLICATE_PAYMENT', 'BEFORE_ORDER_CREATED')),
  suggested_order_id  BIGINT       REFERENCES orders(id),
  status              TEXT         NOT NULL DEFAULT 'OPEN' CHECK (status IN (
                        'OPEN', 'RESOLVED_TO_ORDER', 'RESOLVED_TO_BALANCE', 'REJECTED')),
  resolution_note     VARCHAR(500),
  approval_id         BIGINT,
  resolved_at         TIMESTAMPTZ,
  created_at          TIMESTAMPTZ  NOT NULL DEFAULT now()
);
CREATE INDEX idx_deposit_exceptions_open ON deposit_exceptions (created_at) WHERE status = 'OPEN';

CREATE TABLE invite_relations (
  invitee_user_id  BIGINT       PRIMARY KEY REFERENCES users(id),   -- 每个用户只能被邀请一次
  inviter_user_id  BIGINT       NOT NULL REFERENCES users(id),
  invite_code      VARCHAR(12)  NOT NULL,
  bind_method      TEXT         NOT NULL CHECK (bind_method IN ('APK_CHANNEL', 'CLIPBOARD', 'MANUAL')),
  risk_flags       JSONB        NOT NULL DEFAULT '[]',
  created_at       TIMESTAMPTZ  NOT NULL DEFAULT now(),
  CHECK (invitee_user_id <> inviter_user_id)
);
CREATE INDEX idx_invite_relations_inviter ON invite_relations (inviter_user_id, created_at DESC);

CREATE TABLE invite_reward_rules (
  id                      BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name                    VARCHAR(64)  NOT NULL,
  trigger_event           TEXT         NOT NULL CHECK (trigger_event IN (
                            'INVITEE_REGISTERED', 'INVITEE_FIRST_PAID', 'INVITEE_PAID')),
  beneficiary             TEXT         NOT NULL CHECK (beneficiary IN ('INVITER', 'INVITEE')),
  reward_type             TEXT         NOT NULL CHECK (reward_type IN ('DAYS', 'TRAFFIC', 'BALANCE')),
  reward_value            BIGINT       NOT NULL CHECK (reward_value >= 0),  -- 天 / 字节 / micro-USDT
  reward_percent_bp       INT          CHECK (reward_percent_bp BETWEEN 0 AND 10000),  -- 按订单金额比例（基点）
  min_order_amount_micro  BIGINT,
  freeze_hours            INT          NOT NULL DEFAULT 72,
  daily_cap_per_inviter   INT,
  status                  TEXT         NOT NULL DEFAULT 'DISABLED' CHECK (status IN ('ENABLED', 'DISABLED')),
  starts_at               TIMESTAMPTZ,
  ends_at                 TIMESTAMPTZ,
  version                 INT          NOT NULL DEFAULT 1,
  created_at              TIMESTAMPTZ  NOT NULL DEFAULT now(),
  updated_at              TIMESTAMPTZ  NOT NULL DEFAULT now()
);

CREATE TABLE invite_rewards (
  id                   BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  rule_id              BIGINT       NOT NULL REFERENCES invite_reward_rules(id),
  rule_snapshot        JSONB        NOT NULL,
  inviter_user_id      BIGINT       NOT NULL REFERENCES users(id),
  invitee_user_id      BIGINT       NOT NULL REFERENCES users(id),
  beneficiary_user_id  BIGINT       NOT NULL REFERENCES users(id),
  trigger_ref          VARCHAR(64)  NOT NULL,     -- 例如 first_paid 或 order:123
  reward_type          TEXT         NOT NULL CHECK (reward_type IN ('DAYS', 'TRAFFIC', 'BALANCE')),
  reward_value         BIGINT       NOT NULL,
  status               TEXT         NOT NULL CHECK (status IN ('PENDING', 'REVIEW', 'RELEASED', 'CANCELLED')),
  risk_flags           JSONB        NOT NULL DEFAULT '[]',
  release_at           TIMESTAMPTZ  NOT NULL,
  cancel_reason        VARCHAR(255),
  released_at          TIMESTAMPTZ,
  created_at           TIMESTAMPTZ  NOT NULL DEFAULT now(),
  UNIQUE (rule_id, beneficiary_user_id, invitee_user_id, trigger_ref)
);
CREATE INDEX idx_invite_rewards_release ON invite_rewards (release_at) WHERE status = 'PENDING';
CREATE INDEX idx_invite_rewards_beneficiary ON invite_rewards (beneficiary_user_id, created_at DESC);

CREATE TABLE shared_pay_addresses (           -- 交易所热钱包等公共付款地址
  address        VARCHAR(64)  PRIMARY KEY,
  note           VARCHAR(128),
  auto_detected  BOOLEAN      NOT NULL DEFAULT true,
  created_at     TIMESTAMPTZ  NOT NULL DEFAULT now()
);

-- 6. 节点与流量

CREATE TABLE node_groups (
  id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name        VARCHAR(64)  NOT NULL UNIQUE,
  min_tier    SMALLINT     NOT NULL DEFAULT 1,
  remark      VARCHAR(255),
  created_at  TIMESTAMPTZ  NOT NULL DEFAULT now()
);

CREATE TABLE nodes (
  id                      BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  group_id                BIGINT       NOT NULL REFERENCES node_groups(id),
  name                    VARCHAR(64)  NOT NULL,
  country_code            CHAR(2)      NOT NULL,
  city                    VARCHAR(64)  NOT NULL,
  region                  VARCHAR(32)  NOT NULL,          -- ASIA / EUROPE / AMERICAS ...
  host                    VARCHAR(255) NOT NULL,
  probe_port              INT          NOT NULL DEFAULT 443,
  status                  TEXT         NOT NULL DEFAULT 'MAINTENANCE'
                          CHECK (status IN ('ONLINE', 'OFFLINE', 'MAINTENANCE', 'DISABLED')),
  weight                  INT          NOT NULL DEFAULT 100,
  capacity_users          INT          NOT NULL DEFAULT 500,
  is_recommended          BOOLEAN      NOT NULL DEFAULT false,
  load_score              SMALLINT     NOT NULL DEFAULT 0 CHECK (load_score BETWEEN 0 AND 100),
  online_count            INT          NOT NULL DEFAULT 0,
  agent_cert_fingerprint  CHAR(64),
  agent_version           VARCHAR(32),
  last_heartbeat_at       TIMESTAMPTZ,
  sort_order              INT          NOT NULL DEFAULT 0,
  created_at              TIMESTAMPTZ  NOT NULL DEFAULT now(),
  updated_at              TIMESTAMPTZ  NOT NULL DEFAULT now()
);
CREATE INDEX idx_nodes_group_status ON nodes (group_id, status);

CREATE TABLE node_inbounds (
  id             BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  node_id        BIGINT       NOT NULL REFERENCES nodes(id),
  protocol       TEXT         NOT NULL CHECK (protocol IN (
                   'VLESS_REALITY', 'TROJAN', 'SS2022', 'WIREGUARD', 'HYSTERIA2')),
  port           INT          NOT NULL CHECK (port BETWEEN 1 AND 65535),
  public_params  JSONB        NOT NULL,     -- 可下发客户端的参数：SNI、Reality 公钥、short_id、WG 服务端公钥等
  priority       INT          NOT NULL DEFAULT 100,
  status         TEXT         NOT NULL DEFAULT 'ENABLED' CHECK (status IN ('ENABLED', 'DISABLED')),
  created_at     TIMESTAMPTZ  NOT NULL DEFAULT now(),
  UNIQUE (node_id, protocol, port)
);

CREATE TABLE node_enroll_tokens (
  id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  node_id     BIGINT       NOT NULL REFERENCES nodes(id),
  token_hash  CHAR(64)     NOT NULL UNIQUE,
  expires_at  TIMESTAMPTZ  NOT NULL,
  used_at     TIMESTAMPTZ,
  created_by  BIGINT       NOT NULL,
  created_at  TIMESTAMPTZ  NOT NULL DEFAULT now()
);

CREATE TABLE node_user_events (
  id              BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,   -- agent 增量游标
  credential_id   BIGINT       NOT NULL REFERENCES device_credentials(id),
```

### 10.4 数据库角色与权限

```sql
-- 迁移角色：表的所有者，只在执行迁移时使用，业务服务不使用
CREATE ROLE yuhai_migrator LOGIN;

-- 业务服务（app-api、worker）
CREATE ROLE yuhai_app LOGIN;
GRANT SELECT, INSERT, UPDATE ON ALL TABLES IN SCHEMA public TO yuhai_app;
REVOKE UPDATE, DELETE, TRUNCATE
  ON balance_ledger, subscription_ledger, device_bind_logs, admin_audit_logs
  FROM yuhai_app;
REVOKE DELETE, TRUNCATE ON chain_transfers, orders FROM yuhai_app;

-- 后台服务（admin-api）：同样不能修改流水，只能通过审批执行业务函数写入新流水
CREATE ROLE yuhai_admin LOGIN;
-- 授权方式同上，另按需收紧

-- 报表与审计只读
CREATE ROLE yuhai_readonly LOGIN;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO yuhai_readonly;
```

表的所有者可以删除触发器，所以业务服务绝不能使用所有者角色连接数据库。触发器与权限回收是两道独立的防线。

### 10.5 对账查询示例

```sql
-- 余额快照与流水累加是否一致（每日任务，结果应为空）
SELECT b.user_id, b.available_micro, COALESCE(SUM(l.amount_micro), 0) AS ledger_sum
  FROM user_balances b
  LEFT JOIN balance_ledger l ON l.user_id = b.user_id
 GROUP BY b.user_id, b.available_micro
HAVING b.available_micro <> COALESCE(SUM(l.amount_micro), 0);

-- 已固化的链上转入是否都有归宿（结果应为空）
SELECT id, tx_hash FROM chain_transfers
 WHERE confirm_status = 'SOLIDIFIED'
   AND match_status   = 'UNPROCESSED'
   AND created_at < now() - interval '10 minutes';

-- 链上到账总额 = 已匹配订单金额 + 异常到账金额（按日核对）
SELECT date_trunc('day', block_time) AS day,
       SUM(amount_micro) FILTER (WHERE match_status = 'MATCHED')   AS matched,
       SUM(amount_micro) FILTER (WHERE match_status = 'EXCEPTION') AS exception,
       SUM(amount_micro)                                           AS total
  FROM chain_transfers
 WHERE network = 'TRON' AND confirm_status = 'SOLIDIFIED'
 GROUP BY 1 ORDER BY 1 DESC;
```

## 11. 接口设计

### 11.1 通用约定

| 项 | 约定 |
|---|---|
| 服务入口 | App API：`https://api.{主域名}/v1`（经 CDN/WAF，另有签名的备用域名清单）；节点控制面：`https://node.{控制面域名}/node/v1`（mTLS）；后台：`https://admin.{内网域名}/admin/v1`（仅管理区）；版本检查：`/app/version`（免登录，CDN 缓存 5 分钟） |
| 契约 | OpenAPI 3.1，契约先行。`api/openapi/app.yaml`、`node.yaml`、`admin.yaml` 生成 Dart 客户端（openapi-generator）与 Go 服务端桩代码（oapi-codegen），CI 校验代码与契约一致 |
| 格式 | JSON，UTF-8，字段名 `snake_case`；客户端必须忽略未知字段 |
| 金额 | 字符串，最多 6 位小数，例如 `"100.0043"`；服务端按 micro-USDT 整数解析，超出精度直接拒绝而不是四舍五入 |
| 流量 | 整数字节 |
| 时间 | RFC 3339，UTC，例如 `2026-09-11T08:00:00Z`；响应附带 `server_time` 供客户端校准倒计时 |
| 分页 | 游标分页：`?limit=20&cursor=...`，响应返回 `next_cursor`（为空表示没有更多） |
| 语言 | 按 `Accept-Language` 返回 `message` 文案，错误码与语言无关 |
| 版本 | 路径主版本号。新增字段属于兼容变更；破坏性变更发布 `/v2`，`/v1` 至少保留 6 个月，并通过 `min_supported_code` 引导升级 |

**响应结构**

```json
// 成功：HTTP 2xx
{ "data": { ... }, "request_id": "01J7Z3K4Q8M2T6" }

// 失败：HTTP 4xx / 5xx
{
  "error": { "code": 40902, "message": "设备数量已达上限", "details": { "device_limit": 3 } },
  "request_id": "01J7Z3K4Q8M2T6"
}
```

错误码为 5 位整数：前 3 位等于 HTTP 状态码，后 2 位为序号（例如 `50301` = HTTP 503 的第 1 种情况）。完整列表见 11.7。

### 11.2 请求头与鉴权级别

| 请求头 | 说明 |
|---|---|
| `Authorization: Bearer {access_token}` | 访问令牌（JWT，15 分钟） |
| `X-Device-Id` | 设备 `device_uid` |
| `X-Timestamp` | Unix 秒，与服务器偏差不超过 300 秒 |
| `X-Nonce` | 128 bit 随机数，Base64url，10 分钟内不可重复 |
| `X-Signature` | 设备私钥对规范化请求的签名，算法与规范化规则见 12.2 |
| `Idempotency-Key` | 客户端生成的 UUIDv4，同一业务操作重试时保持不变 |
| `X-App-Version` / `X-Platform` | 例如 `1.0.0+100` / `ANDROID`；低于最低支持版本返回 `42601` |
| `X-Request-Id`（响应） | 与响应体 `request_id` 相同，用户反馈问题时提供 |

鉴权级别：

| 级别 | 要求 | 适用 |
|---|---|---|
| S0 | 无需登录 | 版本检查、引导配置 |
| S1 | 访问令牌 | 只读查询 |
| S2 | 访问令牌 + 设备签名（时间戳、nonce 防重放） | 所有写操作、获取连接凭证 |
| S2-自签 | 请求体携带设备公钥，并用对应私钥签名（证明持有私钥） | 注册、恢复账户 |

### 11.4 关键接口详情

#### 注册：`POST /v1/auth/register`

```http
POST /v1/auth/register
X-Device-Id: 0b6f3c1e-8a52-4d7e-9f10-2c4b7d9e1a33
X-Timestamp: 1789110000
X-Nonce: h7Qm0x2Zk9rT4pWbJ1eYvA
X-Signature: MEUCIQD...
Idempotency-Key: 5f0e2b6c-3d1a-4c8e-b7f2-9a6d0e4c1b85
```

```json
{
  "device_uid": "0b6f3c1e-8a52-4d7e-9f10-2c4b7d9e1a33",
  "device_pubkey": "MFkwEwYHKoZIzj0CAQYIKoZIzj0DAQcDQgAE...",
  "platform": "ANDROID",
  "model": "Pixel 9",
  "os_version": "16",
  "app_version": "1.0.0+100",
  "fingerprint_hash": "3b1f...e9",
  "invite": { "code": "K7M3QP", "method": "APK_CHANNEL" }
}
```

响应 `201`，带 `Cache-Control: no-store`：

```json
{
  "data": {
    "account_no": "8302571644",
    "account_secret": "YH-7KQ2-MX9R-TAHD-4PWN-3E8C",
    "invite_code": "Q4T8NZ",
    "invite_bound": true,
    "device_id": "4812",
    "tokens": {
      "access_token": "eyJhbGciOiJFZERTQSIs...",
      "access_expires_at": "2026-09-11T08:15:00Z",
      "refresh_token": "rt_2Hk9...",
      "refresh_expires_at": "2026-10-11T08:00:00Z"
    },
    "server_time": "2026-09-11T08:00:00Z"
  }
}
```

- 邀请码无效时仍然注册成功，`invite_bound = false`，不暴露失败原因。
- 幂等重放：同一 `Idempotency-Key` 且请求体哈希一致时返回首次结果。为此幂等记录中的 `account_secret` 字段单独用 AES-256-GCM 加密保存，10 分钟后由任务清除该字段；超过 10 分钟的重放返回 `40401`，客户端引导走"恢复账户"。
- `device_uid` 已存在时返回 `40901`，客户端重新生成 `device_uid` 与设备密钥。

#### 恢复账户：`POST /v1/auth/restore`

```json
{
  "account_secret": "YH-7KQ2-MX9R-TAHD-4PWN-3E8C",
  "device_uid": "9c2d...",
  "device_pubkey": "MFkwEwYH...",
  "platform": "IOS",
  "model": "iPhone 16",
  "os_version": "26.0",
  "app_version": "1.0.0+100"
}
```

| 结果 | HTTP | 响应 |
|---|---|---|
| 成功 | 200 | 与注册相同的 `tokens`，不再返回账户密钥 |
| 密钥错误 | 401 / `40104` | 统一文案"账户密钥无效"，不区分格式错误与不存在 |
| 设备已满 | 409 / `40902` | `details.restore_ticket`（5 分钟有效、一次性）与 `details.devices`（名称、平台、最近活跃时间） |
| 尝试过多 | 429 / `42902` | `Retry-After` |

设备已满时，客户端调用 `POST /v1/auth/restore/replace-device`，请求体为 `{ "restore_ticket": "...", "remove_device_id": "4790" }` 加上与恢复请求相同的设备信息，成功后返回令牌。

#### 刷新令牌：`POST /v1/auth/refresh`

请求体 `{ "refresh_token": "rt_2Hk9..." }`，需要设备签名。服务端校验令牌哈希、所属设备与签名公钥一致、`secret_version` 未变化，然后签发新的访问令牌和刷新令牌，旧刷新令牌标记为已轮换。**已轮换的旧令牌再次出现时，整个令牌族立即作废**（返回 `40103`），视为令牌泄露。

### 11.5 节点控制面接口

除注册接口使用一次性令牌外，其余接口都要求 mTLS 客户端证书，服务端从证书中读取 `node_id`，请求体中不携带节点身份。

| 方法与路径 | 频率 | 说明 |
|---|---|---|
| `POST /node/v1/enroll` | 首次部署 | 请求 `{ enroll_token, csr_pem, reality_public_key, wg_public_key, agent_version }`；响应 `{ node_id, cert_pem, ca_chain_pem, cert_expires_at }`。令牌 24 小时有效且只能使用一次 |
| `POST /node/v1/cert/renew` | 证书有效期过去 2/3 时 | 用当前证书申请续期，节点证书有效期 30 天 |
| `GET /node/v1/config` | 启动、`config_version` 变化时 | 入站列表、端口、SNI 与 Reality 目标、agent 运行参数 |
| `GET /node/v1/users/snapshot` | 启动、每 30 分钟校验 | `{ cursor, checksum, users: [{ credential_id, proxy_uuid, proxy_secret, wg_pubkey, wg_address }] }`，只包含该节点所在组可用的凭证 |
| `GET /node/v1/users/events?after={cursor}&limit=1000` | 每 10 秒 | `{ next_cursor, events: [{ event_id, credential_id, present, material }] }`；`present = false` 表示移除，`material` 仅在新增时返回 |
| `POST /node/v1/heartbeat` | 每 30 秒 | `{ agent_version, config_version, snapshot_checksum, cpu, mem, net_rx_bps, net_tx_bps, online_count, kernel }`；响应可携带 `actions`（例如 `RESYNC`、`RELOAD_CONFIG`） |
| `POST /node/v1/traffic` | 每 60 秒 | 请求见 8.5；响应 `{ "accepted": true, "duplicate": false }`，重复的 `report_id` 返回 `duplicate: true` 且不重复累加 |

控制面按节点证书指纹校验 `nodes.agent_cert_fingerprint`，被吊销或被禁用的节点所有请求返回 `40310`。节点接口不经过公网 CDN，只对节点出口 IP 开放。

### 11.6 管理后台接口

**认证流程**

```
POST /admin/v1/auth/login   { username, password }          → { mfa_ticket }（2 分钟）
POST /admin/v1/auth/mfa     { mfa_ticket, totp_code }       → Set-Cookie: yh_admin（HttpOnly; Secure; SameSite=Strict）
                                                              + { csrf_token }，之后写请求携带 X-CSRF-Token
POST /admin/v1/auth/logout
```

**二级验证与审批**

```
L2：POST /admin/v1/step-up { action_code, payload_hash, totp_code } → { step_up_token }（5 分钟，一次性，
    绑定操作与请求体哈希）→ 业务请求携带 X-Step-Up-Token
L3：业务请求（带 step_up_token）→ 202 { approval_id }
    另一名有权限的管理员：POST /admin/v1/approvals/{id}/approve（自身也需 L2 二级验证）
    → 服务端重新校验 payload_hash 与当前数据状态 → 执行 → 审批单 EXECUTED
```

| 接口 | 维度 | 阈值 |

## 12. 安全机制

### 12.1 威胁模型

| 资产 | 主要威胁 | 核心措施 | 章节 |
|---|---|---|---|
| 用户账户 | 账户密钥被猜测或撞库；令牌被窃取后在其他设备使用 | 100 bit 熵密钥 + HMAC 查找 + 限流；令牌绑定设备密钥，写操作要求设备签名 | 4.1、12.2 |
| 用户流量隐私 | 节点记录访问目标；DNS / IPv6 泄漏；节点被入侵 | 节点不开访问日志、不部署 DPI；客户端防泄漏；凭证按设备隔离，可单独吊销 | 3.8、8.8、12.9 |
| 收款正确性 | 收款地址被替换（数据库、后台、传输链路）；伪造到账 | 地址由资金系统离线签名，App 验签；只认链上固化且合约地址正确的转账 | 6.3、6.8 |
| 账务一致性 | 重复入账、重复奖励、重复开通；余额被篡改 | 业务确定性幂等键 + 数据库唯一约束 + 状态机条件更新；流水只追加；每日对账 | 12.3、10.5 |
| 管理权限 | 管理员账号被盗；内部人员滥用 | 管理区隔离 + TOTP + 二级验证 + 双人审批 + 审计哈希链 | 12.4、12.5 |
| 数据库 | 数据泄露、备份泄露 | 敏感字段加密、密钥在 KMS、IP 只存哈希并限期删除、备份加密 | 12.6 |
| 客户端 | 仿冒安装包、被植入代码；本地数据被读取 | 签名证书指纹公示与自检；密钥存安全硬件；截屏防护 | 12.7 |
| 营销资源 | 批量注册刷邀请奖励 | 奖励只在付费后触发 + 冻结期 + 多维关联识别 | 4.5、7.6、12.8 |
| 可用性 | DDoS、域名被封锁、证书吊销 | CDN/WAF、签名的备用域名清单、证书固定备份密钥 | 12.2 |

安全边界说明：设备的合法持有者可以通过 root / 越狱绕过客户端任何检测，客户端措施只能保护"用户免受他人攻击"，不能防止"用户攻击自己的客户端"。因此所有涉及金额、权益、配额的判断一律在服务端完成。

### 12.2 传输与请求安全

**TLS**

- App API 与官网只启用 TLS 1.3，网关兼容 TLS 1.2 时仅允许 ECDHE + AEAD 套件；开启 HSTS。
- 节点控制面使用独立私有 CA 的 mTLS：离线根 CA 签发在线中间 CA，中间 CA 签发节点证书（30 天）。

**证书固定**

- 固定对象为 SPKI 哈希，而非证书本身，证书续期不影响固定。
- 客户端内置至少 3 个 pin：当前使用的密钥、已生成但离线保存的备份密钥、另一家 CA 的中间证书密钥。任一匹配即通过。
- 更换密钥流程：先通过 `/v1/bootstrap`（离线密钥签名）下发新 pin，覆盖到 95% 以上活跃客户端后再切换；紧急情况启用离线备份密钥，无需等待发版。
- 固定失败时不回退到系统信任，直接报错并尝试备用域名。

**签名的引导配置**

`/v1/bootstrap` 返回备用域名列表、pin 集合、最低版本与功能开关，整个配置由离线 Ed25519 密钥签名，App 内置当前与下一把公钥。客户端只接受签名有效且 `issued_at` 比本地缓存更新的配置，防止攻击者通过劫持 DNS 下发伪造域名。

**请求签名（S2 级别接口）**

规范化签名原文（各行以 `\n` 连接）：

```
YH1-ECDSA-P256-SHA256
{HTTP 方法大写}
{路径，不含域名，按 RFC 3986 规范化}
{查询参数按键名排序后 URL 编码拼接，无参数为空行}
{X-Timestamp}
{X-Nonce}
{X-Device-Id}
{请求体 SHA-256 的小写十六进制，无请求体时为空串的哈希}
```

服务端校验顺序：

```
1. |now - X-Timestamp| <= 300 秒，否则 40105
2. 查访问令牌：签名有效、未过期；令牌中的 did 与 X-Device-Id 一致；
   令牌中的 cnf.jkt（设备公钥指纹）与数据库中该设备公钥一致
3. 设备状态为 ACTIVE、账户 secret_version 与令牌一致，否则 40107 / 40108
4. 用设备公钥验证 X-Signature，否则 40102
5. Redis: SET nonce:{device_id}:{nonce} 1 NX EX 600，已存在则 40106
6. 进入业务处理
```

签名解决的是"访问令牌被截获后在别的设备上使用"的问题：即使令牌通过日志、代理或恶意软件泄露，没有安全硬件中的私钥也无法发起写操作或获取连接凭证。

**高风险本地确认**

查看账户密钥、生成迁移二维码、重置账户密钥、移除其他设备，客户端先通过系统生物认证或锁屏密码确认（Android BiometricPrompt，iOS LocalAuthentication）。阶段二增加一把"需用户在场"的独立签名密钥（Android `setUserAuthenticationRequired(true)`，iOS `SecAccessControl` 的 `.userPresence`），服务端对这几类接口额外校验该密钥的签名，使"用户确认过"可被服务端验证。

### 12.3 幂等与防重复

防重复分三层，每一层都能独立发挥作用：

| 层 | 机制 | 作用 |
|---|---|---|
| 接口层 | `Idempotency-Key` + `api_idempotency` 表 | 网络超时重试时返回相同结果，改善体验 |
| 状态层 | 行锁 + 带状态条件的 `UPDATE ... WHERE status IN (...)`，影响行数不为 1 即回滚 | 状态机不可跳转、不可回退 |
| 数据层 | 流水表 `idempotency_key UNIQUE` 与业务唯一约束 | 最终防线：即使上层逻辑出错，同一事实也只能落库一次 |

**幂等键规则**

- 由业务事实确定性构造，不使用随机数或 `now()`，保证任何进程、任何时间重试得到同一个键。
- 冲突时读取已有记录并返回相同结果，而不是报错，使消费方可以无脑重试。
- 所有消费 outbox 事件、执行定时任务的代码必须可重入。

**幂等键清单**

| 场景 | 幂等键 / 唯一约束 | 防止的问题 |
|---|---|---|
| 链上转账入库 | `chain_transfers (network, tx_hash, event_index)` | 同一笔转账被扫描多次 |
| 链上到账入余额 | `deposit:{network}:{tx_hash}:{event_index}` | 重复入账 |
| 转账归属订单 | `orders.chain_transfer_id UNIQUE`、`chain_transfers.order_id UNIQUE` | 一笔钱开通两个订单 |
| 订单扣款 | `purchase:order:{order_id}` | 重复扣款 |
| 权益开通 | `fulfill:order:{order_id}` | 重复开通 |
| 开通失败转余额 | `fulfill_fallback:order:{order_id}` | 重复退回 |
| 异常到账处理 | `exception_credit:{exception_id}`；`deposit_exceptions.chain_transfer_id UNIQUE` | 同一笔异常被处理两次 |
| 客户端下单 | `orders (user_id, client_idem_key)` | 连点或重试生成多笔订单 |
| 报价使用 | `plan_quotes.used_by_order_id UNIQUE` | 同一报价下多单 |
| 金额槽位 | `amount_locks (receive_address_id, amount_micro)` | 同一时段两单同金额 |
| 邀请关系 | `invite_relations.invitee_user_id` 主键 | 重复绑定、改绑 |
| 邀请奖励生成 | `invite_rewards (rule_id, beneficiary_user_id, invitee_user_id, trigger_ref)` | 重复奖励 |
| 邀请奖励发放 | `invite_reward:{reward_id}` | 重复发放 |
| 奖励派生权益 | `traffic_packs (source_type, source_id)` | 同一奖励生成多个流量包 |
| 套餐到期 | `expire:{user_id}:{到期时间 Unix 秒}` | 重复扣除 |
| 流量周期重置 | `period_reset:{user_id}:{period_reset_at Unix 秒}` | 重复重置 |
| 后台调整 | `admin_adjust:approval:{approval_id}` | 审批被执行两次 |
| 设备绑定日志 | `register:{device_uid}`、`restore:{device_uid}`、`revoke:{device_id}` | 重复记录 |
| 节点流量上报 | `traffic_reports (node_id, report_id)` | 重复累加流量 |
| 领域事件 | `outbox_events (event_type, aggregate_type, aggregate_id)` | 重复投递触发重复奖励 |

**对账**

worker 每日执行 10.5 中的对账查询，并额外核对：已完成订单都有且只有一条 `fulfill` 流水；已释放奖励都有且只有一条 `invite_reward` 流水；链上到账总额与资金系统的归集报表一致。任何不一致立即告警并冻结相关用户的余额使用，人工核查后解除。

### 12.4 管理后台安全

**访问控制**

- 后台只部署在管理区：必须先接入零信任网关或运维 VPN，再叠加 IP 白名单，公网无法解析和访问。
- 密码使用 Argon2id（内存 64 MB、迭代 3、并行 4），最少 12 位，禁止使用常见泄露密码。
- TOTP 遵循 RFC 6238（30 秒步长，允许前后各 1 个步长），`totp_last_step` 防止同一验证码在有效期内被重复使用；TOTP 密钥加密存储。
- 会话：绝对有效期 8 小时，空闲 30 分钟过期；登录 IP 的 /24 前缀变化时要求重新验证；Cookie 为 HttpOnly、Secure、SameSite=Strict，写请求校验 CSRF 令牌。
- 连续 5 次登录失败锁定 15 分钟，并通知安全负责人。

**角色与职责分离**

| 角色 | 权限范围 | 限制 |
|---|---|---|
| 超级管理员 | 管理员与角色、App 版本发布 | 不用于日常操作，至少 2 人持有，登录即告警 |
| 运营 | 套餐、邀请规则、公告、黑名单 | 不能调整余额 |
| 客服 | 用户与订单只读、封禁、移除设备、发起调整申请 | 不能审批自己的申请 |
| 财务 | 异常到账处理、余额调整审批、收款地址管理、对账报表 | 不能管理管理员 |
| 运维 | 节点、入站、注册令牌、系统参数 | 不能查看资金数据 |
| 审计 | 全部只读 + 审计日志校验 | 无任何写权限 |

**验证级别**

| 级别 | 要求 | 示例 |
|---|---|---|
| L0 | 已登录 | 查询、查看报表 |
| L1 | 已登录 + CSRF | 编辑节点备注、草稿套餐 |
| L2 | 二级验证：重新输入 TOTP，得到绑定"操作 + 请求体哈希"的一次性令牌（5 分钟） | 封禁、移除设备、改价、黑名单、导出 |
| L3 | L2 + 另一名有权限的管理员审批（同样需要 L2） | 调整时长/流量/余额、异常到账处理、导入收款地址、管理员变更、发布版本 |

L3 审批的约束：

- 发起人与审批人不能是同一人（数据库 `CHECK` 约束兜底）。
- 执行时重新计算请求体哈希并与审批单比对；目标数据在审批期间发生变化（例如用户余额已变动）时拒绝执行并返回 `40908`。
- 审批单 24 小时未处理自动过期；执行使用 `admin_adjust:approval:{id}` 幂等键。
- 单笔上限：余额调整超过 100 USDT、时长调整超过 90 天时，审批人必须是超级管理员；每名发起人每日调整总额设上限。

**敏感信息展示**

- 后台永远无法查看用户账户密钥（数据库只有 HMAC）。
- 付款地址、设备指纹等默认脱敏显示，点击"显示完整"需 L2 并写入审计日志。
- 导出文件带水印（管理员账号 + 时间），导出行为需 L2，导出文件 24 小时后自动删除。

**后台重置账户密钥**

匿名账户没有手机号或邮箱可供核验，客服重置密钥前必须取得以下任一强所有权证明，仅凭口述信息或交易哈希（链上公开可查）不能重置：

1. 用户在仍处于登录状态的设备上生成的一次性客服验证码（设置页"联系客服"，10 分钟有效，由设备签名生成）。
2. 用户使用曾向本账户订单付款的 TRON 地址，对客服给出的随机挑战文本进行消息签名（交易所提币地址无法提供此证明）。

重置后旧密钥立即失效、所有设备下线，新密钥只在一次性查看链接中展示一次，链接 30 分钟有效且打开即焚。

### 12.5 审计日志与哈希链

- 所有后台写操作（包括被拒绝的尝试 `DENIED`）写入 `admin_audit_logs`，记录变更前后数据、二级验证与审批单号。
- 哈希链：`row_hash = SHA-256(prev_hash || JCS(本行除 row_hash 外的字段))`，JCS 为 RFC 8785 规范化 JSON；首行 `prev_hash` 为 64 个 `0`。
- 写入时在事务内获取 `pg_advisory_xact_lock(审计链锁 ID)`，保证链是串行的。
- 锚定：worker 每小时把最新 `id` 与 `row_hash` 写入启用对象锁（WORM）的外部存储，并推送到独立的告警频道。事后即使有人拿到数据库所有者权限重写整条链，也会与外部锚点不一致。
- 校验：后台"操作日志"页可选择区间重新计算哈希链，每日任务自动校验前一天的数据。
- 保留：审计日志至少保留 3 年，只能归档不能删除。

### 12.6 数据保护

**字段加密**

- 信封加密：KMS 中的主密钥（KEK）包装数据密钥（DEK），DEK 解密后只存在于进程内存。
- 密文格式：`版本(1 字节) | key_id(4 字节) | nonce(12 字节) | 密文 | tag(16 字节)`。
- 附加认证数据（AAD）为 `表名.列名.主键`，防止把 A 行的密文复制到 B 行后仍能解密。
- 加密字段：`device_credentials.proxy_secret_enc`、`admin_users.totp_secret_enc`、幂等记录中的注册响应密钥字段等。

**账户密钥 pepper**

pepper 存于 KMS，服务启动时加载到内存。由于服务端只在用户输入密钥时才能接触到明文，pepper 轮换采用"双查找"：新旧 pepper 同时计算查找键，命中旧键的账户在本次恢复时迁移到新键。

**密钥清单与轮换**

| 密钥 | 存放位置 | 常规轮换 | 泄露时处置 |
|---|---|---|---|
| API TLS 证书 | 网关 / CDN | 90 天自动续期（SPKI 可保持不变） | 吊销，启用备份 pin 对应密钥 |
| JWT 签名密钥（Ed25519） | KMS | 90 天，新旧 `kid` 并存 15 分钟 | 立即轮换，访问令牌最多 15 分钟后全部失效 |
| 字段加密 KEK | KMS | 每年，重新包装 DEK | 轮换 KEK 与 DEK，后台任务重加密 |
| 账户密钥 pepper | KMS | 不常规轮换 | 双查找迁移 |
| 收款地址签名密钥 | 资金系统离线设备 | 每年；App 内置当前与下一把公钥 | 暂停全部收款地址，发布强制更新替换公钥 |
| 引导配置签名密钥 | 离线设备 | 每年；App 内置双公钥 | 启用下一把公钥 |
| 节点根 CA / 中间 CA | 根离线，中间 CA 在 KMS | 中间 CA 每年，节点证书 30 天 | 吊销中间 CA，全部节点重新注册 |
| Android APK 签名密钥 | 离线硬件密钥 | 不轮换（必要时用 APK 签名方案 v3 的密钥轮换证明） | v3 轮换并公告新指纹 |
| Reality 私钥 / WireGuard 服务端私钥 | 各节点本地 | 节点重装时 | 该节点换密钥，客户端下次获取配置时更新 |
| 数据库凭证 | 密钥管理服务动态签发 | 24 小时 | 吊销 |

**数据最小化与保留**

| 数据 | 保留期 | 说明 |
|---|---|---|
| 注册 IP 哈希与 /24 前缀哈希 | 30 天 | 到期置空 |
| 应用日志 | 7 天 | 中间件统一脱敏：不记录请求体、令牌、账户密钥、连接配置；IP 只记录哈希 |
| CDN / 网关访问日志 | 不超过 7 天 | 在服务商侧配置保留期或关闭 |
| nonce | 10 分钟 | Redis 自动过期 |
| 幂等记录 | 24 小时 | 注册响应中的密钥字段 10 分钟后清除 |
| 过期会话 | 过期后 30 天删除 | — |
| 每日流量统计 | 180 天 | 之后汇总为月度、去除设备维度 |
| 订单、链上转账、资金流水 | 长期 | 财务与对账需要 |
| 审计日志 | 至少 3 年 | 见 12.5 |
| 节点访问日志 | 不产生 | 见 8.8 |

**备份**

PostgreSQL 开启 WAL 归档与时间点恢复，备份在上传前加密，备份密钥与生产密钥分离保存；每月做一次恢复演练并记录恢复时长。

### 12.7 客户端安全

| 项 | 措施 |
|---|---|
| 本地密钥 | 设备私钥在 Secure Enclave / Android Keystore（优先 StrongBox）中生成且不可导出；令牌与账户密钥存 Keychain / EncryptedSharedPreferences |
| 截屏与后台快照 | 账户密钥页、迁移二维码页：Android 设置 `FLAG_SECURE`；iOS 进入后台时覆盖遮罩，检测到截屏时提示风险 |
| 剪贴板 | 复制账户密钥后 60 秒自动清除（仅当剪贴板内容未被替换）；Android 13+ 标记为敏感内容 |
| 安装包完整性 | 启动时读取自身签名证书指纹与内置值比对，不一致时提示"这不是官方安装包"并禁止登录 |
| 代码保护 | Dart `--obfuscate --split-debug-info`、Android R8；符号表只保存在构建机 |
| 运行环境 | root / 越狱 / 调试器 / Hook 框架检测只作为风控信号上报，不直接拦截 |
| 日志 | Release 构建不输出业务日志；诊断导出时再次脱敏并由用户确认内容 |
| 深度链接 | 只处理 `/i/{邀请码}` 格式，参数白名单校验，不通过链接执行任何写操作 |
| 更新 | 校验 APK SHA-256 与签名证书指纹一致后才安装（见 3.10） |

### 12.8 风控与防刷

| 层 | 信号 | 处置 |
|---|---|---|
| 注册 | IP 与 /24 频率、设备指纹黑名单、模拟器与 root 信号 | 限流、拒绝、打风险标记 |
| 恢复账户 | 同 IP 多次失败、同一查找键多 IP 尝试 | 冷却、告警 |
| 下单 | 待支付订单数、短时间大量取消 | 限制下单 |
| 付款 | 付款地址命中黑名单；同一付款地址（排除公共地址）为大量账户付款 | 奖励转人工审核；必要时暂停该账户权益 |
| 邀请 | 邀请人与被邀请人设备指纹、付款地址、IP 前缀相同；邀请人单日新增异常 | 奖励进入 `REVIEW`，超过阈值暂停邀请人奖励 |
| 连接 | 单设备短时间内在多个国家的节点间频繁切换获取配置；凭证被多个来源 IP 同时使用（节点侧只统计并发数，不记录 IP） | 轮换该设备凭证，多次触发后移除设备 |

风险分由规则累加，规则与阈值存在 `system_configs` 中可在后台调整；风险处置一律可人工复核撤销，并写入审计日志。

### 12.9 VPN 数据面与节点安全

- 协议只使用成熟开源实现（Xray-core 的 VLESS-Reality / Trojan、Shadowsocks 2022、内核 WireGuard），不自研加密算法与协议。
- 客户端防泄漏：DNS、IPv6、断网保护与重连窗口期处理见 3.8。
- 节点加固：SSH 仅允许来自堡垒机的密钥登录；nftables 默认拒绝入站，只开放隧道端口与控制面出站；自动安全更新；Xray 以非特权用户运行，node-agent 只保留 `CAP_NET_ADMIN`。
- 滥用控制（不依赖日志）：节点出站默认封禁 TCP 25 端口，降低被用于发送垃圾邮件的风险；单凭证并发连接数上限；机房滥用投诉按节点维度处理（暂停或更换节点 IP），不追溯到具体用户。
- 节点被入侵处置：后台吊销节点证书 → 该节点所有入站下线 → 对曾分配到该节点所在组的凭证执行 `CREDENTIAL_ROTATE` → 重装系统并重新注册。

### 12.10 研发与供应链安全

- 代码仓库开启分支保护；涉及资金、权益、认证的目录（`internal/deposit`、`internal/ledger`、`internal/auth`）配置 CODEOWNERS，必须 2 人审核。
- 密钥不进入代码仓库，CI 运行密钥扫描；生产配置由密钥管理服务注入。
- 依赖扫描：`govulncheck`、`osv-scanner`（Go / npm / Dart），每次合并与每日定时执行；生成 SBOM 随版本归档。
- 许可证扫描：阻止未经评审的 GPL / AGPL 依赖进入客户端（呼应第 0 章第 3 条）。
- 构建隔离：Release 构建与签名在专用构建机进行，签名密钥不接触普通 CI 执行器；构建产物哈希写入发布记录。
- 上线前：阶段二公测前完成一次第三方渗透测试，覆盖 App、App API、后台、节点控制面与充值流程。

### 12.11 安全事件响应

| 事件 | 立即动作 | 后续 |
|---|---|---|
| 数据库疑似泄露 | 轮换数据库凭证、JWT 密钥、字段加密 DEK；全体刷新令牌作废 | 评估泄露范围，按隐私政策与适用法律通知用户 |
| 收款地址异常（签名校验失败上报、对账不平） | 后台一键暂停全部收款地址，新订单返回 `50301` | 资金系统核对地址归属，排查导入链路 |
| 管理员账号被盗 | 禁用账号、作废其全部会话与未执行审批单 | 按审计日志回溯其全部操作并逐项复核 |
| 节点被入侵 | 按 12.9 流程处置 | 同组节点排查 |
| 签名密钥泄露 | 按 12.6 密钥清单处置 | 发布安全公告与强制更新 |
| 仿冒 App 或钓鱼站 | 官网与 App 内公告官方域名和证书指纹 | 向托管商与域名注册商投诉 |

每类事件都要有值班负责人、联系方式和演练记录；阶段二上线前至少完成"暂停收款地址"与"JWT 密钥紧急轮换"两项演练。

## 13. 分发方案

不上架应用商店会显著增加分发与信任成本，这一章给出各渠道的可行做法、限制与风险。相关许可与合规判断见第 0 章与第 14 章。

### 13.1 渠道总览

| 平台 | 主渠道 | 备选 | 兜底 |
|---|---|---|---|
| Android | 官网下载 APK（公司主体完成开发者验证） | — | 高级安装流程 / ADB |
| iOS | TestFlight | Ad Hoc（内测，设备数受限） | IKEv2/IPSec 描述文件（仅提供 VPN 连接，不是完整 App） |

### 13.2 Android 分发

**签名与验证**

- 使用 Android 签名方案 v2/v3，签名密钥存于离线硬件，妥善备份；密钥丢失将无法发布可覆盖安装的更新。
- 官网公示签名证书的 SHA-256 指纹，App 内自检（12.7），帮助用户识别被二次打包的仿冒版本。
- 以公司主体完成 Google 开发者验证并登记包名与签名证书。运营方对 Google 实名不影响终端用户匿名：终端用户不注册、不登录商店。

**开发者验证的影响与应对**

- 2026-09-30 起在巴西、印尼、新加坡、泰国，从参与计划的应用商店安装的应用开始要求开发者验证；2027 年扩展到全球认证设备上的所有应用，官网直装 APK 届时也需开发者已验证。
- 已完成验证：目标市场用户可正常安装。
- 未完成验证或在尚未支持的地区：应用需走一次性"高级安装流程"（含 24 小时等待）或使用 ADB。下载页需为受影响地区提供图文步骤，并明确这是系统机制而非 App 问题。
- 关注可能落地的 on-device ADB 限制（第 0 章提及的相关提案），预留 TestFlight 之外的沟通渠道以便必要时调整策略。

**渠道包（邀请码写入）**

- 采用 APK 签名块自定义区写入渠道信息的方案（原理同 Walle / VasDolly），在已签名 APK 上写入邀请码，不改动被签名内容、无需重新签名。
- 母包只构建一次；渠道包按邀请码在服务端生成并缓存到对象存储，发版时批量失效。
- 发布与生成渠道包后都用 `apksigner verify` 校验 v2/v3 签名完好。

**应用内更新**

启动调用 `GET /app/version`：低于 `min_supported_code` 强制更新；有新版时下载 APK，校验 SHA-256 与新包签名证书指纹与当前一致后用 `PackageInstaller` 安装（需用户授权"安装未知应用"）。任一校验失败则中止并提示从官网获取。

**下载页要素**

版本号、更新时间、文件大小、SHA-256、签名证书指纹；"允许安装未知应用"引导；受影响地区的高级安装流程说明;新旧版本历史与更新说明；官方域名清单与防钓鱼提示。

### 13.3 iOS 分发

**为什么不用企业签名与免费自签**（第 0 章第 1 条的展开）

- 企业签名（Apple Developer Enterprise Program）协议仅允许向组织内部员工分发，面向公众分发违反协议，证书一旦被吊销，所有已安装用户的 App 会立即无法打开。市面上的"企业签"多为租用他人证书，稳定性无保障，且安装包可能被植入代码。
- 免费 Apple ID 自签需 7 天重签一次，且不支持 Network Extension 权限，VPN 功能无法工作。

**TestFlight（主渠道）**

- 需要付费 Apple Developer 账号，App 须通过 TestFlight 构建审核（比正式上架宽松，但仍需符合审核准则，尤其是 VPN、隐私与支付相关条款）。
- 外部测试每个构建最多 10000 名测试员，通过公开链接加入。
- 构建有效期 90 天，需持续发布新构建续期。
- 优点：稳定、系统级信任、支持 Network Extension；缺点：名额上限、依赖 Apple 审核、加入需安装 TestFlight App。

**Ad Hoc（内测）**

用于团队与早期用户：需预先登记设备 UDID（每年上限 100 台/类设备），打包分发。仅适合小规模测试，不作为公开渠道。

**IKEv2/IPSec 描述文件（兜底）**

- 通过 `.mobileconfig` 描述文件下发系统原生 IKEv2/IPSec VPN 配置，用户在"设置"中安装，使用系统 VPN 客户端连接，不需要安装 App。
- 局限：只能连接支持 IKEv2 的节点，没有 App 的节点切换、测速、套餐、充值等功能，也无法使用 VLESS/Reality 等抗封锁协议；描述文件包含凭证，需安全下发（登录后一次性链接）。
- 定位：当用户无法使用 TestFlight（名额满、地区不可用）时，至少保证基础的加密连接可用。

**审核风险预案**

TestFlight 审核不通过或名额长期不足时的优先级：优化描述与合规材料重新提交 → 扩大 Ad Hoc 与 IKEv2 兜底的覆盖 → 评估是否在特定地区通过正式上架（需接受商店的支付与内容条款，与"不上架"目标冲突，需业务决策）。

### 13.4 官网

- 静态站点（Astro）+ CDN，源站与 App API 不同域，降低相互影响。
- 页面：首页、下载页（自动识别平台）、邀请落地页 `/i/{邀请码}`、帮助中心（充值教程重点讲交易所提币"到账数量"、常见问题、防骗提示）、隐私政策、服务条款。
- 邀请落地页把邀请码写入剪贴板作为归因兜底，并按平台跳转对应下载方式。
- 防封锁：域名与 CDN 多备份，App 内置签名的备用域名清单（12.2），主域不可达时自动切换。

### 13.5 分发相关的完整性要求

- 所有可下载产物（APK、mobileconfig）在发布记录中留存哈希，官网展示的哈希由发布流程自动生成，避免人工填错。
- 版本发布走后台 L3 审批，审批通过后才对外可见（`app_versions.status = PUBLISHED`）。
- 灰度：先对一部分用户返回新版本，观察崩溃率与连接成功率再全量。

## 14. 合规、隐私政策与宣传建议

本章为工程与产品层面的合规设计，不构成法律意见。VPN 服务与加密货币收款在不同国家和地区的许可、反洗钱、税务与数据要求差异很大，上线前必须按目标市场咨询当地律师。

### 14.1 基本立场

- 目标市场先行合规评估：逐个确认当地对 VPN 服务、加密货币收款的监管要求，避开明确禁止的市场。
- 数据最小化作为默认：不收集手机号、邮箱、真实身份；不记录用户访问的网站内容（技术措施见 8.8、12.6）。
- 已实现什么就说什么：隐私政策必须与代码实际行为一致，避免"隐私政策承诺不记录、实际却记录"这类最常见也最严重的问题。

### 14.2 隐私政策要点

隐私政策需用普通用户能懂的语言说明：

| 主题 | 说明方向 |
|---|---|
| 收集什么 | 匿名账户标识、设备型号与系统版本、App 版本、聚合流量用量、订单与链上交易信息；崩溃上报默认关闭 |
| 不收集什么 | 手机号、邮箱、真实身份、通讯录、精确位置、浏览内容与目标网站 |
| IP 的处理 | 注册与恢复时用于风控与限流，仅存哈希，30 天删除；连接过程节点不记录访问日志 |
| 为什么收集 | 提供服务、防滥用、财务对账、法律要求 |
| 保留多久 | 引用 12.6 的保留期表 |
| 第三方 | CDN/WAF、TRON 链上数据源、TestFlight（iOS）；不接入广告与第三方统计 SDK |
| 链上信息 | 说明区块链交易公开可查，提示用户注意付款地址与个人身份的关联风险 |
| 用户权利 | 如何删除账户（见 14.5）、如何导出数据、如何联系 |
| 变更与通知 | 政策变更的通知方式与生效时间 |
| 管辖与联系方式 | 运营主体、适用法律、联系渠道 |

配套服务条款需包含：可接受使用政策（禁止将服务用于攻击、垃圾邮件、儿童性剥削内容等违法用途，呼应 12.9 的滥用控制）、付款与退款政策（加密货币付款的不可逆性、异常到账处理方式、余额与套餐的性质）、免责声明、账户与服务终止条件。

### 14.3 反洗钱与收款合规

- USDT 收款可能触及部分地区对虚拟资产服务的监管（登记、KYC/AML、交易监测、可疑交易报告等），需按目标市场法律确认本业务是否落入监管范围以及相应义务。
- 本系统在设计上保留了可支撑合规的能力：完整的订单与链上流水、异常到账人工流程、付款地址黑名单与"公共地址"识别、可导出的对账报表；但是否需要以及如何落地 KYC 取决于法律意见，不在产品默认流程中。
- 资金的归集与出款由独立的资金系统负责，与业务系统隔离，便于分别满足合规与审计要求。
- 制裁与地区限制：按法律意见在下单或收款环节做必要的地区与地址筛查。

### 14.4 宣传用语规范

| 避免 | 建议替代 | 原因 |
|---|---|---|
| 绝对匿名、100% 匿名 | 不需要手机号或邮箱、我们不收集你的真实身份 | 无法证明的绝对化表述有虚假宣传风险 |
| 100% 安全、绝对安全、军工级加密 | 使用成熟的加密协议（可列出 WireGuard 等）、传输全程加密 | 安全没有绝对；具体协议可验证 |
| 无法追踪、完全隐身、政府也查不到 | 我们不记录你浏览的内容 | 夸大且可能诱导用于违法用途 |
| 永久有效、终身套餐 | 明确的时长或流量 | 与服务可持续性不符 |
| 保证解锁任意网站或服务 | 帮助你建立加密连接 | 不对第三方服务的可用性做承诺 |

统一原则：只宣传可验证、已实现的能力；所有营销文案与隐私政策、实际实现三者一致。

### 14.5 账户删除与数据处理

- App 内提供"删除账户"：立即使账户 `BANNED`、所有设备下线、凭证移除、余额清零（余额为预付服务款项，删除即视为放弃，需在条款中写明）。
- 保留义务：订单、链上流水、资金记录因财务与法律要求需按期保留，但与账户的个人可识别关联（如设备信息）在删除后按保留期清理。
- 用户数据导出：提供账户基本信息、订单记录、流水的导出。

### 14.6 邀请与营销合规

- 邀请奖励只做一级（邀请人与被邀请人），不设多级返利，降低在部分地区被认定为传销的风险（第 0 章第 7 条）。
- 奖励为服务内权益（天数、流量、余额），不可提现为法币或加密货币，条款中写明。
- 不诱导用户进行虚假邀请或自我邀请，防刷机制见 7.6、12.8。

### 14.7 未成年人

服务条款声明面向成年人；不主动面向未成年人推广。因不收集年龄信息，采用条款声明与合理措施相结合的方式，具体要求按目标市场法律确认。

## 15. 开发计划

### 15.1 里程碑

| 阶段 | 目标 | 主要交付 | 预计周期 |

### 15.3 阶段一验收标准

- 完整走通：新用户注册 → 备份密钥 → 选套餐 → 生成唯一金额订单 → 后台模拟到账 → 自动开通并刷新到期时间 → 首页模拟连接显示节点、延迟、流量与剩余时间。
- 重复与并发：对同一订单重复触发模拟到账、并发下单同金额、重复上报流量，账目均正确且不重复入账/开通/奖励（自动化测试覆盖）。
- 邀请：A 邀请 B，B 首次付费后 A、B 各获得冻结中的奖励，冻结期满释放；命中防刷规则的奖励进入审核。
- 后台：高风险操作触发二级验证；L3 操作走双人审批；操作日志哈希链可校验；开发工具在生产配置下无法启用。
- 安全自查：请求签名、证书固定、字段加密、限流、脱敏日志按第 12 章落实并通过检查清单。

### 15.4 进入阶段二的前置确认（呼应第 0 章）

以下事项必须在 M2 开工前有明确结论：iOS 分发方案（TestFlight 账号与审核准备）；Android 开发者验证完成；开源内核许可证评审通过；目标市场的 VPN 与收款合规意见；资金系统对接接口（收款地址签名、归集、对账数据）确定。

### 15.5 团队与协作

- 建议角色：客户端（Flutter + 原生各 1–2 人）、后端（Go 2 人）、前端后台（1 人）、节点与运维（1 人）、设计（1 人）、产品与合规协调（1 人）。
- 协作：OpenAPI 契约先行，前后端并行；每两周演示可运行版本；涉及资金、权益、认证的改动强制双人审核（12.10）。

### 15.6 测试策略

- 单元测试重点覆盖金额精度换算、折算计算、幂等键构造、状态机流转、哈希链。
- 集成测试覆盖到账事务、邀请奖励、流量扣减的并发与重复场景（可用测试替身模拟链上数据源与节点上报）。
- 端到端测试覆盖 15.3 的主流程。
- 阶段二增加：真实节点连接的连通性与防泄漏测试（DNS/IPv6/断网）、TronGrid 扫描的对账测试、第三方渗透测试。
